# 空・雲の商用品質受入基準

## 目的と現在の判定

2026-09-08のユーザー要求は、TrueSky級の物理に基づく空・雲を、200米ドル以上の商用製品として
提供できる品質へ引き上げることである。価格は製品の目標であり、価格だけから品質や競合との
同等性を証明しない。現状の判定は**未合格**。単体試験の全件通過を出荷許可に置き換えない。

比較対象の[trueSKY公式製品説明](https://simul.co/)は、GPUで更新する体積雲・大気、リアルタイムAPI、
描画器から独立したSDKを挙げている。既定設定で2～4msを目標としているが、公開説明だけでは
同じGPU・解像度・天候条件でのACSとの速度差は分からない。宣伝上の数値をACSの測定結果としない。
競合SDKや有償素材の取得・組込みはこの品質目標から推定して実行せず、必要なら別途条件を確認する。

## 出荷を止める条件

| 領域 | 合格に必要な証拠 | 現状 |
| --- | --- | --- |
| 共通の雲密度 | 視線・太陽影・環境光が同じ物質領域・時刻・完成密度を使い、詳細度変更時の量と透過率の誤差を計測できる | 細部を除くと平均密度が増減する反例あり |
| 空の物理計算 | レイリー散乱・ミー散乱・吸収の係数、単位、位相関数、太陽方向、地表境界を明示し、独立した高精度積分と照合する | 地表・遮蔽の個別修正あり。円盤の光量校正とHDR保存前露出は未達 |
| 雲の光輸送 | Beer-Lambert則、位相関数の積分、散乱と吸収の関係、次数間の減衰、照明補間の連続性を検証する | 入口・継続等の回帰は通過。極端入力の残件あり |
| 3Dの外観 | 地上・側面・上空・雲内で同じ雲体が見え、積雲・層状雲・積乱雲で違和感のある柱、壁、粒の集合にならない | 壁状の塊と細部不足が残る |
| 動的な外観 | 移流・対流・成長消散・天候遷移が連続し、静止カメラと移動カメラ双方で粗密の周期的な跳びやちらつきがない | 固定入力だけでは未合格 |
| 雲内 | 層の高さにいるだけでなく、カメラ位置の局所密度が正であることを確認し、突入・離脱・濃い内部・薄い縁を検査する | 現在の雲内候補画像は内部の証拠にならない |
| 性能 | 実際に使用したGPU・解像度・画質設定を記録し、定常時と最悪条件のGPU時間・メモリー・更新費用を測定する | RawDX12の空だけで1280×720の昼22～25ms、薄明約122ms。明確に未達 |
| 製品利用 | 通常C++・Editor・配布後のACS Frameworkで同じ設定と描画が動き、寿命・初期化・終了・失敗復帰を確認する | 通常C++診断と両構成ビルド、実Editor ABIの初期化後32フレーム・終了まで合格。UI外観と配布後の再導入は別途必要 |
| 保守と配布 | 公開API、設定保存、版互換、サンプル、ビルド手順、依存物の配布条件、既知制限を検査する | この目標に対する一括検証は未実施 |

## 物理モデルの扱い

- 空の色を任意の色補間だけで成立させず、散乱と吸収から求めた放射輝度を基準にする。
- 物理量の単位、座標系、太陽・視線の向き、係数の出典または導出を実装と文書で対応させる。
- 物理モデル、数値積分の近似、未解像構造の統計近似、作者による見た目の調整を区別する。
- 基準となる物理設定では、見た目の調整を無効にして比較できること。調整を使って数式の不整合を隠さない。
- 高次散乱の近似を完全な多重散乱と呼ばない。未解像四状態の一致を、三次元確率場の物理的正しさの証明と呼ばない。
- CPU/HLSLを同じ誤式で揃えるだけでは合格にせず、独立した解析解・数値積分・保存則で照合する。
- 新しい差分だけでなく既存実装も必ず疑う。既存コメント、関数名、参照式の写し、文字列検査だけを根拠にしない。
- 単位・座標・方向、位相関数の正規化、消散の二重適用、演算と更新の順序、近似が有効な範囲を確認し、
  独立監査の反例を修正前に失敗するテストへ落とす。GPUでは実際の入出力、資源の対応、世代を検査する。

## 文献と既存実装を検証する手順

関連する論文本文・著者の補足資料・公式実装を都度読み、資料名、版、該当節または式、確認日を記録する。
査読、引用数、採用製品、著名な著者は正しさの証明にしない。資料に無い性質をACS側の推測で補った場合は、
その推測と根拠を分ける。読めなかった本文を、要約や宣伝だけで確認済みにしない。

1. 入力、単位、座標、境界条件、散乱次数、定常性、均質性などの仮定を列挙する。
2. 導出を追い、極限、正規化、保存則、対称性、解析解、反例で式そのものを検査する。
3. 論文の算法・公式実装・ACS実装を区別し、離散化、精度、補間、更新順の差を確認する。
4. 独立した高精度参照の収束を確認し、実GPUへ実行時入力を渡して照合する。
   定数式だけの試験はコンパイラーの事前計算になり得るため、実行時演算の証拠と分ける。
5. 対象天候・高度・太陽位置・動きで採用条件を満たすか判定し、採用・限定採用・保留を記録する。

文献評価、既存の数式監査、変更差分監査は重複しない範囲へ分担する。主担当も結論と根拠を確認し、
エージェント間の一致だけで正しいと判断しない。未検証事項を隠さず、後続の失敗試験へ接続する。

## 固定する検証入力

各実行ではコミット、入力設定、実行バイナリー、描画器、使用GPU、解像度、時刻列、カメラ列を保存する。
設定を変えてから以前の画像と比較する場合は、変更点を明示し、同条件の改善として扱わない。

必要な入力群は次を含む。

- 晴天の昼・低い太陽・日没前後と、被覆の少ない積雲・層状雲・厚い積乱雲・雨天。
- 地平線への接線、太陽方向、逆光、地上からの雲底、雲頂の上空、雲体の側面。
- 空から雲へ、雲から空へ、局所密度の正負を確認した連続した飛行経路。
- 時刻固定・カメラ固定、時刻だけ進行、カメラだけ移動、両方進行。
- 履歴なしの参照、履歴蓄積の開始、通常更新、天候変更、太陽変更、サイズ変更、提出失敗と復帰。
- 等倍と各軽量化設定。誤差の小さい平均だけでなく、局所輪郭・薄い雲・雲縁・濃い内部を分けて測定する。

参照積分は標本数を増やして収束を確認し、その残留誤差と保存形式の丸めを記録する。
許容差は参照の誤差・保存精度・用途から先に決め、候補実装の誤差を見てから広げない。
測定条件や許容差が未確定の項目は未合格のまま残す。

## 性能の初期計測条件

このPCにはRTX 4070 SUPERが搭載されているが、搭載GPUの列挙だけでは描画時に使用したGPUを証明できない。
実行時のアダプター情報を記録し、初期の比較候補を1920×1080と2560×1440、60fpsのフレーム予算とする。
これは最低動作環境や速度保証の確定ではない。販売対象GPUと各画質段階の上限は実測後に明示する。

空・雲の合計GPU時間について4msを初期の設計予算とし、平均だけでなく95・99百分位と最大値を記録する。
この予算を満たすために物理入力や雲の被覆を勝手に減らさない。満たせなければ未達として、
重複計算、空間集約、時間再利用、資源更新のアルゴリズムを見直す。
低解像度診断、CPU側の提出時間、シェーダーコンパイル時間をGPU描画時間の代用品にしない。

初回準備・再初期化・天候変更時の停止時間も別に測る。長いコンパイル中にUIや通常C++アプリが固まる、
準備失敗を隠す、未完成世代を描画する場合は出荷しない。実行中のメモリー増加と終了時の未解放も検査する。

2026-09-12の実解像度検査は[大気積分の記録](AtmosphereViewIntegralResearch.md)を参照する。
今回の時刻測定は初期2フレームを除く10回で、長時間の95／99百分位や最悪条件の網羅ではない。
空だけで予算を超えるため、次の性能改善は検証済み積分の再利用を優先する。
再利用する表の書込み・GPU読出し・CPU読戻しの座標、太陽・高度・媒質変更時の更新も先行試験で固定する。
円盤の[遮蔽と光量の監査](PhysicalSunDiscResearch.md)では、光量校正だけの候補が通常HDRの保存上限へ
飽和することも確認した。係数の縮小や保存時の切り詰めで解決済みにしない。

## 現在の実装順

各段階はTDDで進める。正しい期待動作のテストを先に作り、実際の失敗とその原因を保存する。
最小実装で通過させた後に整理し、回帰・GPU・実画像を再検証する。既知の不具合を再現できたことは
原因の証拠であって、正しい動作の合格ではない。未実装の足場や失敗中の版を出荷用devへpushしない。

1. 完成密度の領域平均を失う反例を製品GPUで再現し、形状・房・侵食の共同変動を含む参照を作る。
2. 追加監査で判明した、直接描画の地表交点・太陽直射の不整合を先行テストで修正する。
   通常C++とEditorのRaw DX12でも使われ得るため、単なる予備経路として後回しにしない。
3. 同じ完成密度を集約する方式へ置き換え、空領域、量、透過率、影との整合性を確認する。
4. 実生成体積と連続飛行で厚み・雲内・動的変形を検証し、柱・壁・粒状化・ちらつきを解消する。
5. 大気と雲の照明を同じ太陽・座標・物理単位へ揃え、レイリー／ミー散乱と吸収の参照比較を完了する。
6. 実解像度の性能・耐久・配布後の通常C++／Editor／Framework検証を揃える。TrueHDRIとGIはこの基盤の後へ置く。

各段階は独立監査を挟み、検証済みの小さな単位でdevへpushする。新しい重大不整合が見つかった場合は
依存関係と影響から順番を更新する。既存の[検証記録](CloudPerformanceVerification.md)には、修正済み・未修正・
未実行を分けて残す。全項目の証拠が揃うまでは「商用品質を保証済み」「TrueSkyと同等」と表示しない。
