# Cloud Performance Verification

`profile_cloud_quality.ps1` は、ACS の体積雲を同じ条件で再測定できる受入ハーネスである。
同じ 3D fixture を次の 3 視点で取得する。

- `horizon`: 地平線を含む、ほぼ水平の視点。
- `zenith`: 可視範囲の大半が雲になり得る、上向き 89 度の視点。
- `above`: 高度約 10 km から浅く見下ろし、青空と雲頂を同じ画角へ入れる視点。

3 回の実行は無人かつ直列で行う。既存 Editor の自動実行経路
(`--show-profiler`、`--hide-grid`、`--interaction-soak`、
`--automation-output-root`、`--profiler-capture`、`--camera3d`) を使うため、
別の描画器や合成計測経路は持たない。

## Run

```powershell
$editor = ".\acs\editor\AcsEditor\bin\Release\net10.0-windows\win-x64\AcsEditor.exe"
$project = "C:\path\to\RenderingShowcase\RenderingShowcase.acsproject"

.\acs\scripts\profile_cloud_quality.ps1 `
  -EditorExe $editor `
  -Project $project `
  -SoakSeconds 30 `
  -Monitor secondary
```

`-Project` must point to a prepared cloud showcase whose configured initial
scene is the intended 3D scene. The harness deliberately does not manufacture
or silently substitute a fixture; the editor report must prove that the loaded
scene rendered real 3D cloud work.

An explicit monitor index is also supported:

```powershell
.\acs\scripts\profile_cloud_quality.ps1 `
  -EditorExe $editor -Project $project -MonitorIndex 1
```

既定の出力先は `TEMP` 配下の重複しないフォルダーである。`-OutputRoot` には別の既存フォルダーを
指定でき、その場合の `-OutputDirectory` は出力ルートの子でなければならない。検証処理は
`--automation-output-root` で同じルートを Editor へ渡す。両プロセスが個別にドライブ直下、
再解析ポイントを含む親経路、出力ルート外への経路を拒否する。既存の報告、計測結果、ログ、要約は
上書きしない。

この作業環境で検証物を `C:\dev\acs_temp_builds` へ集約する場合は、次のように明示する。

```powershell
$outputRoot = "C:\dev\acs_temp_builds"
$output = Join-Path $outputRoot "CloudQualityCandidate-20260823"

.\acs\scripts\profile_cloud_quality.ps1 `
  -EditorExe $editor -Project $project `
  -OutputRoot $outputRoot -OutputDirectory $output `
  -Monitor none
```

The editor and project inputs must be non-empty regular files rather than
reparse-point leaves. Input hashes are read without writer/delete sharing.
This prevents a concurrent writer from producing a hash of partially replaced
content. Provenance includes the editor app host, managed assembly, native
`acs_editor_abi.dll` renderer, dependency manifest, runtime configuration, and
project manifest; hashing only the small app host is not accepted as renderer
identity. The harness keeps read-only, non-writer/non-delete-sharing leases on
all six inputs for the complete run, closing the check-to-launch
replace-and-restore window rather than relying only on before/after hashes.

Editor は `--unattended` で起動するため、どの視点もマウス／キーボード入力を受けず、
自分から前面へ出ない。`-Monitor secondary` は 3 回の取得を最初の有効な副画面へ固定する。
配置をホスト側へ任せる場合だけ `-Monitor none` を使う。

`-DryRun` は出力作成や Editor 起動を行わず、入力を検証して 3 本の正確なコマンドを表示する。
`-SelfTest` は他の parameter を付けずに実行し、合成 report の解析・検証境界に加えて、
終了 code `0`、終了 code `7`、時間切れ、標準出力／標準エラーの非同期排出、子 process の
後始末を短い隔離 process で検査する。Editor 起動や GPU 処理は行わない。

`verify_editor.ps1 -Mode full` は、この GPU 非依存の `-SelfTest` を
`rendering / cloud profiler harness self-test` として実行する。fast／managed mode には
含めない。完全検証ではハーネス契約を毎回確認しつつ、機材依存の FPS を build gate にはしない。
実際の horizon／zenith／above 取得は、明示的な release 性能検査として別に実行する。

## Fail-closed quality evidence

Each scenario must prove all of the following:

- report result is `PASS`, with no report or capture faults;
- observed editor cadence has real samples;
- a non-suppressed 3D view rendered non-zero work with clouds enabled;
- completed GPU queries and the native GPU pass window are available;
- cloud frame/pass timings are finite and positive;
- viewport and cloud trace resolutions are coherent;
- cloud scale is exactly `0.25`, with 384 view samples and 8 light samples;
- cloud work was attempted and submitted;
- temporal history was available and reused without invalidation, with TSR
  enabled;
- 定常フレームは視線積分、時間再構成、雲内部の影キャッシュ、3D受光面用ワールド雲影の
  計4回の計算ディスパッチと、合成描画1回だけであり、一度限りの雑音生成が計測区間へ
  混入していないこと。影テクスチャ自体は `96 x 32 x 96` と `256 x 256` を保ち、安定時の
  1回のディスパッチでは4位相のうち `48 x 32 x 48` と `128 x 128` を更新した処理量として
  記録する。内部影は一つの起動スレッドが同じXZ列の32高度を必ず書くため、論理出力
  `48 x 32 x 48` に対する起動数は `48 x 48` でなければならない。
- 有効呼び出し数、端数を含む起動スレッド数、視線・光・ワールド雲影の最大試料数が、
  各内訳と合計で一致すること。
- native render, Dispatcher heartbeat, GPU retry/fallback, ready-after-retry,
  and renderer-fairness diagnostics are present.

JSON is decoded as strict UTF-8. Numeric schema fields must be finite JSON
numbers of the appropriate integer or duration shape: `null`, numeric strings,
`NaN`, infinities, fractional counters, and out-of-range counters fail closed.
Boolean fields must be JSON booleans rather than `0`/`1` or string lookalikes,
and status enums are case-sensitive.
GPU query count may not exceed query capacity, and zero-work fields must be
reported explicitly rather than omitted or represented by `null`.

horizon、zenith、above の品質 snapshot は項目ごとに比較する。viewport／trace 解像度、
品質 flag、query window 設定、dispatch 数、TSR、最大試料処理量は完全に一致しなければならない。
したがって、カメラ変更だけで雲品質を下げ、見かけの性能を上げることはできない。

## 解像度による原因切り分け

Editor の `Rendering/CloudRenderScale` は内部描画の品質倍率であり、`1.0` は画面寸法の
`1/4`、`2.0` は `1/2`、`4.0` は等倍になる。通常の品質・性能検査は`1.0`を使い、
出力解像度の履歴へ16段階で再構成する。`4.0`は全画素を毎フレーム描画するため、低解像度描画や
時間再構成が形状の乱れを作っているかを目視で切り分ける場合だけ使う。通常描画と同じ384刻みを
保つので、比較対象を画面解像度へ限定できる。

通常描画では、各細密区間の長さと密度の重みを保ったまま、区間内の採取位置だけを
`p_i = frac(p_0 + i * (sqrt(2) - 1))` でずらす。同じ相対位置を全区間で採ると、地平線で広がった
刻み幅が基本形状の周期と一致した際に、同じ密度だけを繰り返し拾って細かな粒や縞になるためである。
384個の位相は16区画へ各24個が入り、採取数やテクスチャ取得数を増やさずに共振を分散する。
通常描画の開始位相`p_0`は区間中央`0.5`へ固定し、後続区間だけを上の決定論的な列で分散する。
参照描画は比較画像を決定的に保つため、この分散も使わず全区間の中央`0.5`へ固定する。

`Rendering/CloudReferenceMode=true`は内部描画を等倍へ固定し、時間再構成を無効にして、視線レイの
刻み上限を512へ増やす。通常C++利用側では`CVolumetricClouds::SetReferenceMode(true)`が同じ役割を
持つ。刻み上限の7/8を実積分、1/8を空領域から細密領域へ戻る余裕へ使うため、通常384刻みは336分割、
参照512刻みは448分割になる。現在は通常描画の実レイ画素も現在の形状・不透明度へ置換し、積分位置を時間平均しないため、
開始位相を毎フレーム変えない。`CloudRenderScale=4.0`でも乱れが残り、参照描画だけで消える場合は
刻み数または区間位相が原因である。参照描画でも残る場合は、密度場または照明式を監査する。どちらも常用時の
性能基準ではなく、原因を分離するための診断設定として扱う。

### 時間平均しない開始位相の修正

以前の通常描画は画素とフレームから視線積分の開始位相を乱数化し、時間再構成では16フレームごとに
乱数列を進めていた。一方、解決処理は等倍画素とそのフレームの16位相採取画素を現在値で置換し、
過去の積分位置を色へ平均していなかった。「時間平均する」という前提と実際の処理順が一致せず、
積分誤差だけが画面上で変化する状態だった。

開始位相を区間中央`0.5`へ固定し、通常描画では区間番号による無理数列だけを残した。地上、雲中、
上空の同一視点で、時間変化する粒状感が減り、旧来の放射状反復が現れないことを確認する。これは
形状密度、テクスチャ採取数、最大刻み数、16位相の画素配置を変更しない。

Editor の雲負荷契約は、通常描画の `trace pixel数 * 384` と、全解像度かつ時間再構成なしの参照描画に
限った `trace pixel数 * 512` を別々に受理する。最大光採取数は、受理した実際の最大視線採取数へ8を
掛けて検証する。これにより参照描画を未知の負荷として誤って拒否せず、192段など契約外の値は拒否する。

時間履歴には地平線の部分被覆を掛ける前の雲色、不透明度、代表深さを保存する。地平線被覆は
通常合成と大気対応合成の最終画素で一度だけ求め、不透明度へ適用する。被覆を履歴へ保存した後で
次フレームにも掛けると、被覆を`c`とした履歴が`a_n = a_0 * c^n`で減衰する。16段階再構成のうち
15回が履歴だけになる画素では、`c = 0.5`が`0.5^15`まで消えてから実標本で戻り、地平線に周期的な
欠けを作るためである。既存の全解像度画素中心と横・縦の隣接視線から求める解析的被覆を後段へ
移すだけなので、視線積分数とテクスチャ取得数は増えない。画素中心の同次遠点は全画面三角形の
三頂点で逆射影して線形補間し、横・縦の隣接遠点は逆射影行列の対応行から求める。したがって、
全画素で逆射影行列を掛け直す費用も追加しない。

## 遠方座標での視線復元

空と雲の視線方向は、カメラ位置を含むビュープロジェクション行列を反転した後で
カメラ位置を引いて求めてはならない。例えばカメラが `(64000, 1, 96000)` にある場合、
遠方平面のワールド座標とカメラ位置はどちらも大きな値になる。単精度で両者を保持してから
差を取ると、差に必要な下位桁が既に失われ、隣接画素の視線が同じ値へ丸められる。この誤差は、
雲では大きな格子模様、通常の空では細い四角形の輪郭として現れる。

`BuildCameraRelativeInverseViewProjection()` は、ビュー行列から平行移動を除き、回転と投影を
合成してから反転する。シェーダーはこの行列で得たカメラ相対座標をそのまま正規化し、密度場を
採取するワールド位置が必要な箇所だけ、最後にカメラ位置を加える。処理順は次のとおりとする。

`視線 = normalize(逆(平行移動なしビュー * 投影) * クリップ座標)`

`ワールド位置 = カメラ位置 + 視線 * 視線距離`

ビュー行列を作る前にも同じ注意が必要である。既知の向きを `注視点 = eye + direction` へ変換すると、
遠方では加算時点で方向の下位桁が失われる。`CCamera::SetLookDirection()` は原点で回転を作ってから
平行移動を加える。エディターの視点、シーンカメラ、通常C++の自由カメラ、軌道カメラは、向きを
既に持っている場合にこの入口を使う。

同じ契約を、雲だけでなく環境空、物理大気、局所霧にも適用する。物理大気の体積表生成は
揺らぎなしのカメラ相対逆行列を使い、深度から表面距離を復元する合成と解析的な太陽円盤は、
深度を書いたTAAの画面揺らぎを含むカメラ相対逆行列を使う。シェーダーは復元した相対位置の
`length()`を直接使い、大きなワールド位置からカメラ位置を引かない。

既存の `CVolumetricClouds::RenderCompute()`、`CSkyAtmosphere::BuildAerialPerspective()`、
`CompositeAerialPerspective()`、`CompositeLocalFog()`、`CImageBasedLighting::DrawSkybox()`、
`DrawEnvSkybox()` は互換性のため残す。遠方座標を扱う新しい呼び出し元は、それぞれの
`CameraRelative`入口へカメラ相対逆行列を明示的に渡す。エディター、通常の`CSky`、
`ALegacyScene3DAdapter`は同じ補助関数を使い、実装ごとの計算差を作らない。

物理大気と局所霧は別の体積表へ焼く。物理大気だけの処理では高さ霧を、局所霧だけの処理では
Rayleigh散乱、Mie散乱、大気表参照を分岐で省く。現在の高さ霧はX/Z方向に一様なので、同じ向きと
高さのまま水平移動しても再生成しない。物理大気もカメラ高度を別の入力で持つため、水平位置を
再生成キーへ含めない。品質の採取数や体積表解像度を下げず、無効な媒質の計算だけを除く。

時間履歴の再投影でも、大きなワールド位置を一度作ってから前カメラ位置を引いてはならない。
現在の雲までの相対位置へ「現在カメラ位置－前カメラ位置」と風の逆移流量だけを加え、前フレームの
カメラ相対位置を直接作る。

`前相対位置 = 現在視線 * 雲距離 + (現在カメラ位置 - 前カメラ位置) - 風移動量`

この位置を前フレームのカメラ相対ビュープロジェクション行列へ掛ける。深度整合性も
`length(前相対位置)` で判定し、ワールド座標同士の差を使わない。

2026-08-21 の目視検査では、参照描画、画面内雲解像度 `864 x 438`、視線採取数 `512`、
時間再構成なしの条件で確認した。原点ではなく `(64000, 1, 96000)` へカメラを置いた天頂視点で、
修正前に再現していた雲の格子模様と空の四角形の輪郭がともに消えた。通常描画でも16段階の時間再構成を
収束させた後、同じ遠方座標の天頂と地平線で輪郭状の履歴破綻や全面黒化がないことを確認した。
単体試験では、向きと投影が同じ原点カメラと遠方カメラから得るカメラ相対逆行列が許容誤差内で
一致することに加え、空、雲、大気、霧、環境光、時間再構成、深度合成、エディター、通常C++
アダプターの全経路が同じ契約を使うことを固定する。軌道カメラは原点と遠方で同じ角度を与えた時の
カメラ相対行列が一致すること、水平移動では物理大気と高さ霧の生成回数が増えないことも検査する。

2026-08-22 の上空比較では、被覆 `0.60`、遠方座標 `(64000, *, 96000)`、表示寸法 `864 x 438` を固定した。
通常描画は `216 x 110`、192段、時間再構成ありで雲GPU平均 `4.51 ms`、参照描画は等倍、512段、
時間再構成なしで平均 `39.08 ms` だった。参照描画でも白く平坦な雲頂が残り、局所霧と空気遠近法を
無効にした通常描画でも残った。この条件では、採取数、時間再構成、後段の媒質合成ではなく、密度場と
照明の釣り合いを次に監査する。

同日の通常品質計測では、内部寸法倍率 `0.25`、視線採取数 `192`、光採取数 `8`、時間再構成ありの
同一条件で品質判定を通過した。雲処理時間は地平線が平均 `2.14 ms`、最大 `3.21 ms`、天頂が平均
`1.05 ms`、最大 `1.70 ms` であり、GPU計測から換算した平均処理能力はそれぞれ `456.17 FPS` と
`778.36 FPS` だった。エディター全体の実測更新頻度に対する `300 FPS` 目標は、CPU処理と画面更新の
待機も含むため参考値として未達だったが、雲品質・処理量・GPU計測の受け入れ条件はすべて通過した。

同じ生成配布物を使い、単一ヘッダーを直接利用する通常の C++ 実行ファイルと、外部 ACS Framework
本体を Debug・Release でビルドして実行した。Framework の単体試験は両構成とも `538` 件中
`0` 件失敗であり、エディター専用経路に依存していないことも確認した。

## Runtime settings safety

`CVolumetricClouds` normalizes every public layer, lighting, range, and upper-
layer setting on the CPU before storing or uploading it. Non-finite values use
the field default; distances, fade, step growth, sample count, transmittance,
phase eccentricity, and contribution ratios are bounded to the ranges declared
in `Sky.h`. An upper layer that cannot remain above the normalized lower layer
is disabled instead of being uploaded as an intersecting or zero-thickness
density band.

Only an effective normalized change invalidates temporal history. Lower- or
upper-layer changes also invalidate the sun-depth cache because they change the
density field. Lighting, distance, and reference-mode changes retain the raw
density cache, while rejecting accumulated screen-space color. The exact and
cached light paths both use the configured `LightExtinction`; no legacy fixed
extinction coefficient is allowed in cache confidence or early termination.

These bounds establish numerical and cache-coherency safety. They do not by
themselves prove that the heuristic density, phase, or multiple-scattering
model is physically calibrated; that remains a visual-reference requirement.

## 雲形状の時間変化

風の移流だけでは密度場全体が同じ方向へ平行移動し、雲の輪郭や内部の盛り上がりは変化しない。
現在の実装は、天候領域と基本形状の第 1 領域をワールド座標へ固定したまま、残りの基本形状領域、
第 2 渦領域、二つの侵食領域へ異なる低速の位相ずれを加える。これにより大きな雲塊の連続性を
保ちながら、輪郭と細部が非剛体に成長・浸食する。

位相ずれは `ResolveVolumetricCloudEvolutionFrameTerms()` が CPU で 1 フレームに一度だけ求め、
視線方向と光方向の密度評価で共有する。既存のテクスチャ採取位置を動かすだけなので、形状、
天候、渦、侵食の採取回数は増えない。時刻 0 では全項が 0 となり従来の密度場を保つ。無風でも
緩やかな対流変形は続き、風速の絶対値が大きい場合だけ変化速度を制限範囲内で上げる。

従来はこれらの形状位相を動かしても、雲が存在するかを決める天候被覆は固定だった。
現在は、天候のゆがみと雲種をそれぞれ `[-1, 1]` の局所係数とし、形状用と細部用の時間位相と
組み合わせる。基礎被覆を `c` 、位相と局所係数から得た有界な変化を `p` とすると、変化後は次式となる。

`c' = saturate(c + clamp(p, -0.14, 0.14) * 16 c² (1 - c)²)`

`c = 0` と `c = 1` で変化量は厳密に 0 となるため、完全な空が一斉に曇ったり、濃い雲の中心が同期して明滅したりしない。
変化が最大になるのは `c = 0.5` の雲縁であり、地点ごとの係数の符号が異なるため、同じ時刻に成長する縁と消散する縁が共存する。
変化後の天候値を占有判定、詳細密度、光方向密度のすべてで共有するため、空間省略と描画結果が食い違わない。
計算は既に採取した値への算術演算だけで、天候テクスチャの採取回数は増えない。

時間再構成は 0.25 秒を超える時刻飛びで履歴を無効化する。Ultra では各出力画素の実標本が
16 フレームに 1 回だけ更新されるため、静止視点で現在値の重みを常に `0.125` にすると、成長または
消散した雲縁まで長く過去形状へ引かれる。現在被覆と履歴被覆の差を `d` とし、静止視点の現在値の
重みを次式で求める。

`w = lerp(0.125, 0.70, smoothstep(0.025, 0.18, d))`

`d <= 0.025` の小さな採取誤差は従来どおり長く平均し、明確な被覆変化だけを最大 `0.70` で現在形状へ
追従させる。カメラ移動中は従来どおり `0.70` を使う。履歴色と深さは既に読み込み済みなので、
この判定は算術演算だけであり、テクスチャ採取回数を増やさない。太陽方向深さキャッシュは、移流だけを
鍵にして古い密度を再利用せず、現在の対流位相を含む密度場から毎フレーム生成する。

対流変形は平行移動ではないため、雲の時間位相が変わったフレームを風の移流だけで再投影すると、
雲底に前フレームの形が筋状に残る。現在は定数バッファの末尾へ前フレームの低速・高速位相を渡し、
現在との差の最大値 `d_e` を `saturate(220 d_e)` で求め、履歴の現在値優先率は
`max(0.08, saturate(220 d_e))` とする。差が `0.08` 未満の安定した画素でも現在値を最低8%混ぜ、
雲の下面や対流の細部が古い位相へ固定されるのを防ぐ。それを超える画素は空間再構成へ戻る。
通常の等倍経路はこれまでどおり現在フレームをそのまま使うため、この補間は時間再構成の未採取画素だけへ
適用する。この追加は位相値の差分と線形補間だけで、雲密度・光採取・テクスチャ採取数は増やさない。

## 雲底と雲頂の対流形状

天候テクスチャの雲種は、周期の異なる二領域を混ぜた後で高さ形状の選択値へ変換する。従来は
`smoothstep(0.34, 0.58, type)` を使っていたが、決定的な生成式を 50 万地点で監査すると、混合後の
中央値は約 `0.541`、10～90 パーセンタイルは約 `0.433～0.637` だった。この分布へ従来式を適用すると
約 60% が積雲側の確定範囲に入り、約 31% は値 `1` に完全飽和した。層雲、層積雲、積雲を使い分ける
という実装意図に反し、広域がほぼ同じ高い形状になっていた。

現在は実分布に合わせて `smoothstep(0.42, 0.66, type)` とする。中央値付近は約 `0.50` となり、全地点の
約 26% が層雲側、約 23% が積雲側、残りが連続した中間形状になる。値域と単調性を保ち、既に採取した
天候値への算術演算だけを変えるため、テクスチャ採取回数は増えない。この修正は雲種ごとの高さ差を
復元するものであり、基礎形状そのものの大きな雲塊を保証するものではない。

2026-08-21 の20秒計測では品質判定を通過し、地平線視点は平均 `3.29 ms`、最大 `4.09 ms`、天頂視点は
平均 `3.25 ms`、最大 `4.37 ms` だった。最大視線採取数 `192`、光採取数 `8`、定常時の雲描画投入数 `2` は
変更前と同じである。雲量 `0.50` の画面比較では高さ形状の種類が戻った一方、密な天頂領域では旧変換と
新変換の両方にワールド XZ 軸へ固定された矩形状の基本形状が残ることも確認した。この既存欠陥は
雲種変換とは分離し、基本形状の生成・採取品質として別に修正する。

雲種ごとの高さ分布を正規化高度へそのまま適用すると、同じ雲種が続く広域で密度の境界も同じ
高さとなり、雲頂が横に平らな層として見える。既に取得した天候値から柱ごとの高さ変形量を求め、
凝結高度より上の雲体へ適用する。
被覆の強い中心は持ち上げ、薄い縁は押し下げる。以前は生の天候値を固定範囲
`smoothstep(0.38, 0.74, weather.r)` へ入れていた。しかし既定雲量 `0.5` で実際に残る天候値は
およそ `0.625` 以上なので、見える柱の大半が同じ中心側となり、説明とは逆に広い雲頂を作っていた。
現在は最終密度と同じ被覆補間値 `m` を使い、`smoothstep(0.08, 0.92, m)` で雲の境界から
中心までの位置を求める。空領域判定用に広げた被覆は柱形状へ使わないため、雲量を変えても
見える縁は低く、中心は高くなる。後段の密度も同じ `m` を再利用し、テクスチャ採取と被覆計算を増やさない。
層雲では変形量を小さく、積雲または降水域では
最大 `0.18` まで広げる。時間位相を全地点へ同じ符号で加えると、高被覆時には雲面全体が同期して
上下する。そこで、既に採取した低周波のゆがみと雲種をそれぞれ `[-1, 1]` の連続した空間係数へ
変換し、周期の異なる二つの時間位相との内積を柱ごとの局所位相にする。ある地点が上昇中でも別の
地点は下降できるため、無風時にも雲体が一様に呼吸せず、局所的に盛り上がりと沈み込みが進む。

正規化高度 `h`、凝結高度 `c = 0.14`、柱の変形量 `s`、上層倍率 `b` に対し、
`u = saturate((h - c) / (1 - c))` とした変形後高度は次式とする。

`h' = h                                            (h <= c)`

`h' = c + (1 - c) saturate(u - s * 16 u² (1 - u)² b)  (h > c)`

下層では `b = 1`、薄い上層では `b = 0.30` とする。以前は `4 h (1 - h)` により雲底直上も柱ごとに
上下し、地上から煙の房が垂れたように見えていた。現在は `h <= 0.14` を恒等変換として雲底を固定する。
四次式は凝結高度と層上端で値と傾きを連続させ、中央では従来と同じ最大変形量を保つ。
導関数を変える項の絶対値は最大約`3.079 |s| b`であり、`|s| <= 0.18`では下層でも導関数が
約`0.445`以上となる。このため区間全体で単調増加し、高さが折り返して同じ柱に不連続な密度面を
作らない。変形後高度は高さ分布だけでなく基本形状の三次元採取座標にも使う。

目視確認では、雲量 `0.85` の入力は広い曇天として残り、雲量だけを `0.50` にした一時複製では
空の抜けと柱ごとの高低差を確認できた。一方で輪郭には薄く流れた部分がまだ多く、今回の修正だけで
大きな積雲塊の品質を達成したとは扱わない。次の形状改善では、この被覆境界を保ったまま大域形状と
雲種ごとの隆起量を監査する。

この変形が対象とするのは雲体内部の密度境界である。曲面雲層そのものが遠方で地平線へ収束して
生じる画面上の境界は物理層の交差結果なので、この式では移動させない。

視線密度で求めた雲種、降水量、柱の変形量は、採取間隔に応じて侵食帯域を制限する近距離3点へ共有する。
遠距離5点は毎フレーム作る影キャッシュが各地点の天候、渦、柱形状を採取する。キャッシュを
利用できない場所も、視線位置の値を既定の2500 m層で最大約2.05 km先まで流用せず、各光標本の天候、雲種、降水、
柱高、基本形状を再評価する。渦は基本形状の座標を最大44 mしか移動させないため視線標本から共有し、最小約315 mの天候模様は
必ず地点ごとに採取する。通常のキャッシュ採用経路ではテクスチャ採取回数を増やさない。単体試験は層の両端、値域、全許容変形量での単調性、上層の抑制、および近距離共有と遠距離
再採取の境界を検査する。局所位相は算術演算だけで求めるため、視線密度の天候採取回数は増えない。
時刻 0 では二つの時間位相がともに 0 となり、従来の静的な柱形状と完全に一致する。

## 高さ分布の二重適用防止

雲種ごとの高さ分布は、基本形状を雲として採用するしきい値へ反映する。この値を最終密度へも
そのまま掛けると、同じ高さ変化を二度適用し、地平線に近い視線では層境界が水平な濃淡の段として
強調される。現在は、しきい値用の重みが `0.12` に達するまでだけ滑らかに閉じ、それより内側では
最終密度を減らさない。基本形状の三次元ノイズが輪郭を決める範囲を広げつつ、物理層の端では密度を
確実にゼロへ戻す。

視線の空領域判定、詳細密度、追加テクスチャ採取をしない低詳細度密度、近距離と遠距離の光採取は、
すべて同じ層端用重みを使う。この変更は算術演算だけであり、テクスチャ採取回数を増やさない。

## 基本形状の分散維持

基本形状は周期と向きの異なる四つの3次元領域を採取する。以前は各領域を
`0.45 : 0.27 : 0.17 : 0.11` の正値加重平均にしていた。独立した値を平均すると模様の反復は弱まるが、
形状の分散も同時に失われる。各領域を0〜1の16段階で全組み合わせした検査では、平均値は`0.5`のまま、
分散が単一領域より小さい`0.0298822`まで低下していた。このため空と雲の境界が狭い値域へ集まり、
上空から見た大きな雲塊が平らな濃淡へ潰れていた。

この段階では第1領域を主形状として残し、第2〜第4領域から`0.5`を引いた値を
`0.30 : 0.18 : 0.10`で加えた。0〜1の一様な検査値では分散を戻せたが、実際に焼き込まれる
Perlin-Worley分布の中心を測っていなかった。後続監査で実平均が約`0.669`だと判明し、
`0.5`中心とこれらの重みは廃止した。現在の式は「基本形状の実分布と雲体連結性の監査」を参照する。

同じ上空カメラで通常描画と、等倍・512段・時間再構成なしの参照描画を確認した。大形状の濃淡は
現れたが、両方とも細かな房状の輪郭が不足しており、ぼけた面に見える問題が残った。旧式との改善幅は
上記の数値検査で保証し、見た目の完成をこの検査から推定しない。侵食係数だけを強めた比較にも
視認できる改善がなかったため、その調整値は採用していない。この修正を超高品質な雲の完成とは扱わず、
細部密度と照明を分離して確認する次の監査を継続する。

## 細部侵食の処理順

上空の参照描画を、不透明度、全放射輝度、直接光、単散乱へ一時的に分離して確認した。
不透明度には大形状しかなく、全放射輝度と直接光はさらに平坦だった。詳細体積の分散だけを
約3倍へ戻す比較も、列積分後の不透明度を視認できるほど変えなかったため採用していない。

原因は詳細値ではなく適用順にあった。以前は基本密度を詳細値で侵食し、その後で天候被覆、
高さ形状、降水補正を掛けていた。基本密度が`1`の雲芯は侵食後も`1`のため、最後に掛ける
滑らかな高さ形状が雲頂を決め、詳細体積は実際の表面を変えられなかった。

現在は基本密度、天候被覆、高さ形状、降水補正から0～1の粗密度を先に確定し、その粗密度を
詳細値で侵食する。基本密度`1`、被覆`0.75`、高さ閉鎖`0.20`、詳細値`0.60`、侵食量`0.24`の
境界例では、旧順序の最終密度`0.15`に対して補正後は約`0.00701`となる。詳細を無効にした場合は
同じ粗密度へ戻り、追加のテクスチャ採取もない。上空の不透明度表示では空隙と不規則な雲頂輪郭が
現れることを確認した。一方、通常照明ではこの細部がまだ弱い。単一散乱だけの診断では空隙と
大域的な陰影が通常照明より明確になったため、多重散乱と環境光が表面コントラストを埋めている。
ただし、多重散乱へ空の遮蔽をそのまま掛ける比較と、既定係数だけを下げる比較は改善が小さく、
調整値を採用していない。照明の式と密度採取を分けて監査し、見た目だけで係数を決めない。

## 房状隆起の高さ方向帯域と局所自己影

詳細体積の第1 Worley成分を同じ周辺分布の二領域から採取し、その差を基本形状のしきい値へ加える。
差そのものの期待値は0なので、雲域全体を一方向へ太らせず、同じ時刻に膨張する縁と侵食される縁を作る。
ただし、非線形なしきい値処理と密度飽和を通した後の平均密度が厳密に不変になるとは扱わない。
移動量の上限は雲底の`0.018`から
雲頂の`0.082`まで連続的に増やす。基本形状の遷移幅`0.22`に対し、最大移動は雲底で約8%、雲頂で約37%である。
空領域判定には同じ最大移動量を含め、詳細値を読む前に正の隆起を捨てない。

最初の試作では既に採取した2次元天候場を高さ方向へ固定し、70%を房の芯、30%を3次元詳細へ割り当てた。
上空では改善が小さい一方、地上では高さ方向へ伸びた柱と矩形状の輪郭が現れた。完全に同じ信号を雲層全体へ
通す設計が原因なので、この方式と値は採用していない。

採用した方式は3次元詳細体積を維持し、高さ方向の採取帯域だけを修正する。以前の領域Aは横`0.0011`に対して
縦`0.0018`、領域Bは横`0.0023`に対して縦`0.0030`であり、第1 Worley成分の代表的な変化幅はそれぞれ
横約227 m／縦約139 m、横約109 m／縦約83 mだった。縦方向の方が細かいため、2500 mの雲層を積分する間に
隆起と侵食の符号が何度も変わり、不透明度へ残らなかった。縦尺度をA=`0.00055`、B=`0.00115`へ下げ、
代表幅を約455 mと約217 mにする。横の約2倍だけ縦へ連続させるため、柱にはならず、G成分の高周波侵食も残る。
既存の二回の詳細体積採取を使うので、テクスチャ採取、描画投入、GPU資源は増えない。

通常照明では高次散乱が近距離の詳細自己影まで弱い消散率で通り、房の濃淡を埋めていた。太陽方向8点のうち、
詳細体積を評価する最初の3点の光学的深さを`tau_near`、残りを`tau_far`、高次散乱の消散縮小率を`m`とする。
二次・三次散乱の透過率を次式へ分ける。

`T2 = exp(-(tau_near * sqrt(m) + tau_far * m))`

`T3 = exp(-(tau_near * m + tau_far * m²))`

遠距離は従来どおり次数ごとに光を回し、細部を採取した近距離だけ一段前の縮小率で自己影を保つ。
`tau_near=0`、または`m=0`と`m=1`では従来式と一致する。既に積分済みの3点を分けて保持するだけなので、
追加採取はない。環境光、雲底の地面反射、一次散乱は変更せず、広い雲面を一律に暗くする調整も行わない。

2026-08-22の参照描画では、雲量`0.42`、密度`2.1`を固定し、地上と約10200 mの上空に加えて、
手続き天候場を数値探索した高被覆地点`XZ=(42000 m, 42000 m)`を確認した。地上では青空と白い雲頂を保ち、
棄却した試作の縦柱は消えた。上空では輪郭と局所的な濃淡が増えたが、UE級の完成品質とはまだ扱わない。
次の監査では、時間を固定した同一密度場の画像差分と、表面法線を追加採取なしで近似できるかを扱う。

通常品質は雲量`0.50`、密度`2.1`、`CloudRenderScale=1.0`、参照描画なしで各20秒計測した。
地平線は平均`2.97 ms`・最大`3.62 ms`、天頂は平均`1.24 ms`・最大`1.98 ms`で、両視点とも品質ゲートを
通過した。GPU照会の平均時間からの換算値は地平線`322.39 FPS`、天頂`675.85 FPS`である。Editor全体の300 FPS目標は
参考値未達だが、最大視線標本192、最大光標本8、1/4解像度の時間再構成、雲影更新量は規定値と一致した。

`a5ac188b`のソースからDebug・Release配布物を隔離生成し、44件の実体ファイルとmanifestの計45件を
生成元と配置先で照合した。manifestのSHA-256は
`6791A8F69CC8F20BCB1113A5FB542568B9D955C7E239A2568940B17D43682B15`、単一ヘッダーは
`781999C83582DF1BD88C284F06D387C22C480F7E6E47597CAFAB214A532122AD`だった。今回の変更は実装cppに閉じるため、
単一ヘッダーの内容は前回配布から変わらず、両構成のライブラリとmanifestだけが新しい実装を保持する。
正規の通常C++ consumerは両構成でコンパイル、リンク、実行に合格した。

外部ACS Framework `5ba0200`も同じ隔離配布物を明示参照し、Debug・Releaseとも本体をビルドできた。
単体試験は両構成でそれぞれ538件中0件失敗だった。Release実行を8秒以上継続し、3D描画、青空から分離した
薄い雲、時間経過による雲模様の微小変化、終了を確認した。Framework既存の`AcsEnumReflection.h:90`にある
`C4267`警告は両構成で残るが、今回の配布物による新規警告ではない。

## 自己遮蔽の位相分散と環境光

一つの視線内で太陽方向の疎な積分をすべて同じ位相から始めると、採取誤差が同じ高さへ揃い、
遠近法によって横縞として見える。視線上の採取番号 `i` と黄金比の小数部 `φ` を使い、光採取の
開始位相を `j_i = frac(j_view + i φ)` とする。192 個の視線採取では 16 個の位相区画へ各 11〜13 個が
入り、特定の高さへ偏らない。光円すいの8方向は、この開始位相から従来どおり黄金角で回す。
通常描画と参照描画の `j_view` は決定論的であり、同じ入力から時間ノイズを加えない。通常描画は
視線区間番号による位相分散を残し、参照描画は全視線区間を中央へ固定する。

## 太陽方向積分の区間中央採取

太陽方向の各採取区間は長さが指数的に増える。以前は区間終端の密度へ区間全長を掛けていたため、
散乱点の直近が濃く、終端が薄い雲縁では局所的な光学的深さを過小評価していた。区間内で密度が
一次的に変化する場合、終点法には傾きに比例する誤差が残るが、区間中央の密度へ区間長を掛ければ
積分値と一致する。

現在は進行量の半分だけ進めて密度を採取し、同じ半分をもう一度進めて区間終端へ到達する。
主描画の近距離3点と遠距離5点、影キャッシュを作る遠距離5点で同じ順序を使う。近距離3点の後に
影キャッシュを引く位置は従来と同じ区間終端なので、正確な経路とキャッシュ経路の境界はずれない。
密度の採取回数とテクスチャ採取回数は増えず、各採取点でベクトル加算が一つ増える。

## 光路密度と上層倍率の統一

自己遮蔽に使う密度は、視線密度と同じ被覆、高度、降水量、上層設定を使う。以前の遠距離5点と
影キャッシュは基本形状と高さ分布だけを使い、雲底から雲頂へ `1.10` から `0.92` へ変える密度補正、
降水域を最大 `1.28` 倍にする補正を落としていた。近距離3点から遠距離5点へ切り替わる位置で、
同じ雲の消散係数が別の式になるため、降水域の自己遮蔽を過小評価していた。

現在は高さ `h` と降水量 `r` による倍率を次式へまとめ、詳細侵食を使う視線・近距離経路と、
侵食を省く遠距離・影キャッシュ経路で共有する。

`S(h, r) = lerp(1.10, 0.92, h) * lerp(1.0, 1.28, r)`

上層では被覆倍率を密度の飽和処理より前、濃さ倍率を飽和処理より後へ適用する。この順序は既存の
視線密度と同じである。既定の上層設定では被覆が `0.55`、濃さが `0.30` なので、両方を落とした
光路は意図した上層密度を最大で約6倍に見積もり得た。両倍率は密度を確定する関数の内部だけで
適用し、呼び出し元や巨視的採取結果の構造体へ保持しない。光円すい全体へ一時値を持ち越さず、
追加のテクスチャ採取も発生しない。

2026-08-22時点では、各層の密度積分を基準光学的深さ`1.6`へ写し、厚さ`H`に対して
`s = 1.6 / H`を消散へ使っていた。この式は一様密度なら任意の層を`H * s = 1.6`にするが、
後の単位監査で、層厚が増えても光学的深さが増えない誤りと判明した。2026-08-26以降は
`1.6 / 2500 m = 0.00064 m^-1`を基準消散係数とし、900 m、2500 m、9400 mの一様層は
それぞれ`0.576`、`1.6`、`6.016`になる。

現在は密度採取時に確定した上層・下層の判定を再利用し、視線の不透明度、近距離と遠距離の太陽光、
動的自己遮蔽キャッシュ、3D受光面用ワールド雲影の全経路で、その標本が属する層の尺度を選ぶ。
光円すいの基準間隔だけは層厚から別に求める。上層用の消散係数と採取間隔はCPUで一度だけ計算するため、
GPUの標本数、テクスチャ採取数、定数バッファーの大きさは増えない。層判定に使った高度も
巨視的密度標本へ保持し、密度式ごとに同じ高度を再計算しない。

## 上下層の晴天域を標本予算から除外

下層と上層を一つの外殻として交差判定し、層間は密度`0`なので粗く通過すればよいとしていた。しかし、
視線歩進は交差区間の全長を固定標本数で割って刻み幅を決め、ワールド雲影も同じ全長を32点へ分割する。
このため密度を採らなくても晴天域の距離が刻み幅を広げ、実際の上下層へ使える標本数を減らしていた。

現在は下層と上層を独立した二つの曲面区間として交差判定し、視点から近い順へ並べる。主描画の
細密・粗密刻みは両区間の実長の和から求め、区間間は標本を消費せず次の入口へ移る。後続層の先頭は
必ず細密区間を一度確認するため、薄い上層を粗い採取位相だけで飛ばさない。ワールド雲影の32点は
各区間の長さに比例して配り、二層がある場合は各層へ最低1点を確保する。定数バッファーは既存の
`float4`配置を保ち、未使用だった成分へ上層底面・上面の二次方程式項を格納する。

下層`2600～12000 m`、上層`15000～17000 m`を鉛直に見る検査では、従来の外接区間は`14400 m`、
雲が存在し得る実区間は`11400 m`、晴天域は`3000 m`となる。32点は下層26点・上層6点へ分かれ、
晴天域には配置されない。上下から見た区間順序、主描画、環境キューブマップ、3D受光面用雲影で
同じ二層交差規則を使う。

2026-08-22 の実画面検査では、上層 `7400～9200 m` を有効にした通常 C++ の ACS Framework を
地上から5秒以上動かし、停止、明暗の跳ね、シェーダー生成失敗がないことを確認した。上層の
自己遮蔽は働くが、地平線付近には帯状の密度が残り、超高品質な雲の合格状態ではない。

上空で雲が欠落したように見えた最初の比較は、視点から約 `200 m` の狭い範囲だけを見ており、
偶然に雲の空隙へ入っていた。雲殻との交差区間と地面側の地平線制限を監査し、雲底より上では
地面側の打ち切りが無効になることを確認した。約 `10200 m` から数 km の範囲を見下ろす比較では
下層雲が表示されたため、上空描画の欠落とは判定しない。ただし Editor はまだ上層設定を公開して
いないため、上層設定の公開は別工程として残す。

環境光の遮蔽にカメラまでの透過率を使うと、同じ雲でも視点を動かしただけで空と地面反射の明るさが
変わる。また、太陽方向の細い光円すいから得た `tau_light` は直接光用の経路であり、空半球または
地面から届く拡散光の代表経路ではない。これを流用すると、太陽が高いほど全天空光まで直接影と
同じ形で失われ、厚い雲が一様な灰色へ沈む。

上下積算キャッシュを追加する前の局所近似では、低詳細度の局所密度 `d`、正規化高度 `h`、
高次散乱で縮小した環境光用消散率 `sigma_ambient` から、各層境界までの鉛直経路を評価していた。
この式は現在もキャッシュ範囲外と上層雲の代替処理にだけ使う。

`d = max(lowLodDensity * Density, 0)`

`sigma_ambient = 0.60 * MultiScatterOcclusion^2 * LightExtinction`

`tau_sky = d * (0.35 + 0.65 * (1 - h))`

`tau_ground = d * (0.35 + 0.65 * h)`

`V_sky = exp(-sigma_ambient * tau_sky)`

`V_ground = exp(-sigma_ambient * tau_ground)`

この局所近似は、既定の `LightExtinction=5` と `MultiScatterOcclusion=0.28`、密度倍率1では、空可視率が雲底で
約 `0.7904`、雲頂で約 `0.9210` となる。消散係数を含めつつ、高次散乱で方向を失った光を直接光と
同じ率では消さない。空の環境光には `V_sky`、地面反射には `V_ground` を掛け、太陽高度、
`tau_light`、カメラ方向の累積透過率は含めない。

2026-08-23 の式監査では、視線と太陽方向の光学的深さが作者指定の `Density` をそのまま保持する一方、
環境光だけが `saturate` により局所密度1で打ち切られていた。たとえば局所低詳細密度1、`Density=2.1`でも
密度1と同じ可視率となり、濃い房を同じ灰色へ揃えていた。上限だけを外し、負値防止は維持した。
同条件の空可視率は雲底で約 `0.6102`、雲頂で約 `0.8412` となる。上空・雲層内の比較では濃い部分だけが
わずかに締まり、全体を一律に暗くする変化ではなかった。ただし見た目の差は小さく、時間再構成による
輪郭の軟化が主因として残るため、この補正だけを品質完了とは扱わない。

通常 C++ の ACS Framework で式だけを差し替えた比較では、雲底の過度な沈み込みは減ったが、
被覆 `0.68`、密度 `2.8`、上層雲有効の天候指定は引き続き空を灰色の連続層で閉じた。これは
散乱式ではなく曇天相当の設定である。晴天表示は被覆 `0.50`、密度 `2.1`、上層の被覆倍率 `0.22`、
濃度倍率 `0.12`へ分け、青空の隙間を保つ。一方、房状の雲頂と内部陰影はまだ不足しているため、
この環境光補正だけを超高品質な雲の完成とは扱わない。

## 高さ比率の未初期化警告防止

下層と上層の高さ比率は同じ関数で選択する。以前は各分岐から直接値を返していたため、式としては
全経路で値が決まるにもかかわらず、FXC がインライン展開後の戻り値を未初期化の可能性ありと判定した。
現在は下層の式で局所変数を初期化し、上層の場合だけ同じ局所変数を上書きして、一つの経路から
範囲を 0〜1 に収めて返す。下層と上層の式、選択条件、範囲制限の順序は変更していない。

単体試験は層外、層端、層内の代表高度で従来の条件式と結果が完全に一致することを検査する。
固定カメラの地平線・天頂実行では、以前の `heightFractionFromAltitude` に対する未初期化警告が
どちらも出ないことを確認する。

## 採取間隔による侵食帯域の制限

侵食用の3次元テクスチャは一つの詳細度だけを持つ。最も細かな成分は約20〜30m、低周波成分でも
約100mの周期なので、地平線方向を数百m間隔で積分しながら詳細度0を読むと標本化できず、時間的な
ちらつきや筋へ変わる。カメラからの距離だけでは、上向きの長いレイと短いレイを区別できないため、
現在は視線レイと近距離の太陽方向積分で、それぞれ実際の刻み幅を使う。

刻み幅が10m以下なら従来の侵食を保ち、10〜48mで高周波成分と侵食量を滑らかに減らし、48m以上では
基本形状へ戻す。最後の端数区間だけ細部が再出現しないよう、各積分区間の長さではなくレイ全体で
一定の刻み幅を使う。侵食寄与が消えた標本では、二つの3次元テクスチャ採取も分岐前に省く。

以前の光採取は、既定の2500 m層で第1～3区間が乱数位相により `13.50～24.00 m`、
`22.28～39.60 m`、`36.75～65.34 m` となるにもかかわらず、3区間すべてへ最高周波数と侵食量を
強制していた。第3区間の一部は48mを越えるため、採取できない細部が時間平均で平らな陰影や
ちらつきへ変わり得る。

現在の光採取はCPUで求めた層別の基準間隔と、区間成長率`1.8`を使う。既定層の第1～3区間は
`8.44～15.00 m`、`15.19～27.00 m`、`27.34～48.60 m` となり、各区間の実間隔で侵食を
滑らかに減らす。第4区間は最小位相でも `49.21 m` なので、遠距離5点は低詳細度密度へ移れる。
採取間隔用の尺度だけは`1.6 / 層厚`を保つが、`layer.w`は固定の基準消散係数`0.00064 m^-1`であり、
両者を流用しない。旧文書と旧テストの約3.2kmという値は採取係数を落として1.6倍へ誤算していたため
訂正した。最大位相で8区間の終端は旧式の
`1991.55 m`から`2047.49 m`、最後の区間中央は`1592.00 m`から`1588.33 m`となる。標本数8と
遠方到達範囲を維持し、追加のテクスチャ採取を行わずに細部帯域と採取間隔を一致させる。

上空の単一散乱比較では、この補正だけで房状の細かな陰影が劇的に増えたとは判定できなかった。
したがって超高品質な雲の完成とは扱わず、採取不能な細部を除く正しさと時間安定性の修正として採用する。
通常照明へ戻した上空・地平線をそれぞれ5秒以上観察し、新しい横縞、粒状ちらつき、明暗の跳ねが
出ないことを確認した。一方、両視点とも雲は白く広い面へ潰れており、房状の雲頂と内部陰影は不足する。
次の照明監査では、多重散乱と環境光を同時に弱める係数調整ではなく、各項のエネルギー上限、遮蔽の
適用先、表面と内部の寄与を数値で分離する。

## 粗密切り替え後の視線採取位相

空領域では粗い間隔で密度の有無を調べ、密度を見つけると一つ前の粗い区間へ戻って細かく積分する。
以前は粗い採取点の位相をそのまま細密積分へ持ち込んでいたため、粗い刻みが細密刻みの2倍となる
代表的な条件では、参照描画の位相 `0.5` が細密区間の境界へ変換されていた。これは「区間中央を使う」
基準画像の契約と一致せず、時間平均を無効にした画像へ高さ方向の積分誤差を固定する。

現在は、粗い採取点から一つ前の区間始点を求め、その位置へ `jitter * fineStep` を加えて細密積分を
始める。開始位相は両経路とも区間中央で、通常描画の後続区間だけを決定論的に分散する。粗い空領域判定、
採取上限、密度評価式は変えず、粗密切り替え時の算術演算だけを変更するため、テクスチャ採取回数は
増えない。

## 視線標本と担当区間の一致

位相付きの位置をそのまま積分区間の始点として扱うと、位相より前の距離を失い、標本位置から
さらに半刻み先を代表深度として記録してしまう。参照描画のように位相が `0.5` の場合、区間
`[100, 110]` を刻み幅 `6` で積分すると、以前は位置 `103` と `109` から長さ `6` と `1` だけを積み、
全長 `10` のうち `7` しか消散へ反映していなかった。一様密度の代表深度も、本来の `105` ではなく
`106.5` へずれていた。

現在は位相付き標本位置 `t_s`、位相 `j`、刻み幅 `d` から担当区間の始点
`c = max(t_s - j d, t_0)` を復元する。担当長は `l = min(d, t_1 - c)` とし、末尾の端数区間では
標本位置を `c + j l` へ収める。上記の例では位置 `103` が長さ `6`、位置 `108` が長さ `4` を担当し、
全長と一様密度の代表深度がそれぞれ `10` と `105` に一致する。消散には担当長、深度モーメントには
実際の標本位置を使うため、通常描画の分散位相でも距離を欠落させない。テクスチャ採取回数と採取上限は
増えない。

## 動的な自己遮蔽キャッシュ

各視線標本から太陽方向へ採取する8点のうち、侵食の影響が大きい近距離3点は従来どおり正確に
積分する。遠距離5点は、`96 x 32 x 96` の `RGBA16F` 3次元テクスチャへ先に積分した光学的深さを
利用する。`RG`には二つの採取模様から求めた平均深さと差、`BA`には空・地面方向の積算密度を保存する。
差がしきい値を超える場所、キャッシュ範囲外、上層雲では遠距離5点も正確な積分へ戻す。

退避経路は各遠距離標本で天候、高さ分布、基本形状を再採取する。以前は視線標本の被覆と
柱形状をそのまま使っていたため、光路が天候模様の雲縁を跨いでも同じ密度が続き、キャッシュを
使えない場合だけ自己影が広い層へ潰れていた。追加採取はキャッシュが完全に採用された画素では
実行されない。渦の差による座標誤差は最大44 mに制限し、任意機能の初期化失敗時も天候境界を跨ぐ誤った密度固定へ戻さない。

密度場は風移流とは別に対流変形するため、キャッシュは毎フレーム更新する。初回、履歴無効、
影の基準格子または投影地図の移動、参照描画では全体を更新する。連続した安定フレームでは
XZまたはXYの偶奇位置を4位相で巡回し、各体積画素・画素を遅くとも3フレーム前までの密度へ
更新する。1フレームの有効呼び出し数は全更新の4分の1になる。影の光路長と密度式は変えず、
環境光の上下積算に限って各高度で粗密度を1回追加採取する。描画を送信できなかった場合は両方の影を無効化し、
次の正常フレームで全体を更新する。

2026-08-21の20秒計測では、同じ入力、同じ表示寸法、同じ視線・光の採取数を保ったまま品質判定を
通過した。雲のGPU平均時間は、全更新時の地平線視点5.40 ms、天頂視点6.58 msから、四位相更新時の
地平線視点3.43 ms、天頂視点3.96 msへ短縮した。短間隔の連続画像では、斜め格子成分の差が画面全体の
変化量の0.33%であり、格子状のちらつきは目視でも確認されなかった。

同日の柱境界修正後の20秒計測も品質判定を通過し、地平線視点は平均 `3.404 ms`、最大 `4.467 ms`、
天頂視点は平均 `5.096 ms`、最大 `6.065 ms` だった。最大視線採取数、最大光採取数、定常時の
ディスパッチ数は修正前と同じで、テクスチャ採取も追加していない。天頂側の増加は、以前ほぼ同じ
高さへ潰れていた中心柱を被覆境界からの位置に応じて持ち上げ、実際に積分される密度領域を戻した
結果として記録する。全更新時の `6.58 ms` は下回るが、今後の大域形状改善ではこの値を基準に
不要な占有領域を増やさない。

以前の二段目は第一段の値を複写するだけで空間勾配を品質判定へ反映していなかったため廃止した。
これによりGPU上の3次元テクスチャは2個から1個へ、生成ディスパッチも2回から1回へ減る。
固定時刻の参照画像では、正確な8点積分に対する相関係数 `0.9992`、平均二乗誤差の平方根 `0.607`、
平均輝度差 `0.071` で、横方向の帯状誤差は約17%減少した。重い参照描画でのGPU時間も
約 `68.5 ms` から `60.0 ms` へ短縮したため、品質と速度の両方を満たす構成として有効化する。

Editor と従来の Scene3D 経路は、描画処理を開始する前に現在の場面から雲照明を更新する。
雲層中央の正規化高度で大気の RGB 透過率を評価し、上下方向の空照明勾配には現在の天頂色、
地面からの反射には現在の下半球色を使う。これにより、太陽が低いときも昼間の白い直接光が
雲へ残る問題と、雲底と雲頂が同じ地平色の環境光を受ける問題を防ぐ。

方向光の近似では、現在地点の密度と区間不透明度が一次散乱の発生量を既に制限する。
二次・三次散乱は周囲にも散乱源が必要なため、低 LOD 密度 `d` と層内の正規化高さ `h` から
周囲散乱源の確率を求め、その係数を高次散乱だけへ適用する。

`pDepth = saturate(0.05 + pow(saturate(d), lerp(0.5, 2.0, saturate((h - 0.30) / 0.55))))`

`fSurround = lerp(1, pDepth, PowderStrength)`

`S = exp(-tau) * phase0`

`  + fSurround * (`

`      a * exp(-b * tau) * phase1`

`    + a^2 * exp(-b^2 * tau) * phase1)`

`PowderStrength` は互換性のため名前を維持するが、現在の意味は `[0, 1]` の混ぜ率である。
この係数は入射光を増幅しない。低 LOD 密度は、最終的な天候被覆と高さのしきい値を用いて、
すでに採取した基本形状から求める。空間を広めに取る空領域判定は流用せず、テクスチャ採取も
増やさない。以前は `fSurround` を一次散乱へ掛け、周囲媒質を必要とする二次・三次散乱を
雲縁でも全量加えていた。この順序では方向性を持つ表面光だけが失われ、等方に近い内部光が残る。
光学的深さ `tau=2`、一次位相 `0.4`、高次位相 `1.0`、既定の `a=b=0.28`、疎な雲頂の
`fSurround=0.715` では、旧順序の合計 `0.26567` に対して補正後は `0.21641` となる。
密な領域では `fSurround=1` のため結果は変わらない。以前の任意な近距離光標本、
`edgeBoost`、および `1.08` のエネルギー増幅は使わない。

`MultiScatterContribution` を `a`、`MultiScatterOcclusion` を `b` とする。実行時の正規化で
`0 <= a <= b <= 1` を保証するため、二次の `a <= b` だけでなく三次の `a^2 <= b^2` も成立し、
縮小後の散乱係数は消散係数を越えない。高次散乱は方向を失う近似として、二次と三次で同じ
有界な位相を使う。これは三次までの有界な近似であり、完全な多重散乱解ではない。
係数縮小と次数加算は Frostbite の
[SIGGRAPH 2016講義資料](https://media.contentapi.ea.com/content/dam/eacom/frostbite/files/s2016-pbs-frostbite-sky-clouds-new.pdf)
に従い、同資料の比較対象である `N=3` まで積算する。密度と高さによる周囲散乱源の分布は Guerrilla の
[Nubis SIGGRAPH 2017雲照明モデル](https://advances.realtimerendering.com/s2017/Nubis%20-%20Authoring%20Realtime%20Volumetric%20Cloudscapes%20with%20the%20Decima%20Engine%20-%20Final%20.pdf)
に従う。引き続き実用向け近似であり、完全な放射輸送を主張するものではないため、固定した
視覚参照の撮影を合格条件として維持する。

通常照明の上空視点と地平線視点をそれぞれ5秒以上観察し、新しいちらつき、白飛び、明暗の跳ね、
停止を起こさないことを確認した。ただし両視点とも広い雲面が白く均され、房状の細部と内部陰影は
まだ不足している。この補正だけを超高品質な雲の達成とは扱わず、上層を含む光学的深さの尺度と
環境光の寄与を引き続き分離して監査する。

## 水滴雲の単散乱アルベド

視線区間の不透明度 `a = 1 - exp(-density * step * ViewExtinction)` は、散乱と吸収を合わせた消散を
既に含む。以前は、この不透明度から発生する直接光へ `SunScatter=0.14` を掛けていた。この値を
単なる明るさ調整として小さくすると、消散した光の大半が吸収された扱いとなり、晴天用の雲量でも
雲塊全体が灰色の面へ沈む。

現在は `SunScatter` を消散に対する散乱の割合、すなわち単散乱アルベドとして扱い、可視光の
水滴雲に近い既定値 `1.0` とする。値は `0～1` に制限し、太陽、空、地表から入る全散乱光へ同じ値を
適用する。太陽付近の強い前方散乱は正規化した位相と位相上限で制御し、有限次数で失う有向光は
独立した `SunScatteringLuminanceScale` で必要な場面だけ補う。補償なしの既定値は `1.0` であり、
追加のテクスチャ採取や視線標本はない。

Editor の実画面では、約 `10200 m` からの見下ろしで暗い灰色の染みだった雲が白い雲塊として
地表から分離し、地上視点でも青空の隙間と白い雲頂を維持した。これは黒つぶれ対策ではなく、
晴天時に灰色の連続面へ見える問題の補正である。一方、地平線付近の水平帯は通常描画でもほぼ同じ形で
残り、参照描画の採取位置だけを分散しても解消しなかったため、採取位相を原因とは判定しない。

## 描画距離減衰の標本単位適用

以前の視線積分は、雲層へ入る距離 `t0` から距離係数 `F(t0)` を一度だけ求め、全区間を通常密度で
積分した後の不透明度へ掛けていた。地平線レイが減衰開始点より手前で雲層へ入る場合、数十～数百 km
先までの密度が全量で積み上がってから一括調整される。この順序では遠方密度がほぼ不透明な横長の面に
なり、青空が残る雲量でも灰色または白色の地平線帯へ見える。

現在は標本距離 `t` ごとに `F(t)` を求め、消散と散乱へ使う密度そのものへ掛ける。

`F(t) = 1 - smoothstep(MaxDistance * (1 - FadeFraction), MaxDistance, t)`

これにより、視線透過率、散乱光、代表深さが同じ減衰済み密度から積分される。完成済みの不透明度だけを
薄める後処理ではない。`FadeFraction=0` は同じ端点を `smoothstep` へ渡さず、`MaxDistance` の直前まで
係数1、終端で0とするため、0除算による非数も作らない。

旧HLSLは減衰区間が無い場合と通常の場合を別々の`return`で返していた。全有限経路で値は決まるが、
FXCはインライン展開後の`cloudDistanceFade`を未初期化の可能性ありとして`X4000`を出していた。
現在は返り値を0で初期化し、有効な区間では`blend² * (3 - 2 * blend)`、区間が無ければ終端前だけ1を
代入して、最後の一箇所から返す。有限値の式と分岐境界は従来の`SmoothStep`と同じで、NaN入力だけは
明示的に0へ倒す。実GPUコンパイルを含むDebug 1415件、Release 1411件の単体試験で`X4000`が消えた。

`8c4a9c95`のソースからDebug・Release配布物を隔離生成し、44件の実体ファイルとmanifestの計45件を
照合した。manifestのSHA-256は
`A7B8529EB56F5F2B0D96215D002A6419A717801B04AF9A70E8334BF7606A2B40`、変更のない単一ヘッダーは
`781999C83582DF1BD88C284F06D387C22C480F7E6E47597CAFAB214A532122AD`だった。通常C++ consumerを

## 晴天雲量と雲種・降水成分の分離

今回の対象は黒つぶれではなく、広い灰色の雲面が空を覆って曇天に見える状態である。雲底の空光と
地面反射をそれぞれ0と1へ振った診断では、通常昼光の見た目を支配するほどの差にならなかった。
根拠なく環境光を増幅して雲の立体感を消さないよう、`AmbientAtBase=0.26`、`AmbientAtTop=0.52`、
`GroundContribution=0.15`の既定値は維持する。Editorからは`CloudAmbientAtBase`、
`CloudAmbientAtTop`、`CloudGroundContribution`で明示的に変更でき、通常C++では既存の
`FVolumetricCloudLighting`を使う。

Editorの上層雲は`CloudUpperBaseHeight`、`CloudUpperTopHeight`、`CloudUpperCoverageScale`、
`CloudUpperDensityScale`で設定できる。上層の高さを下層の上へ置くと、薄い高層雲を同じ視線採取へ
接続し、下層雲との間隔・重なり・空の抜けを一貫して確認できる。高さが無効な場合の既定値は従来どおり
上層雲なしであり、既存プロジェクトの見た目と負荷を変えない。

実画面で曇天感を支配していたのは雲量から天候場しきい値への非線形変換だった。同じ時刻、密度2.1、
物理大気、参照描画で比較すると、雲量0.50は地平線に複数の大きな雲塊が連続し、0.35はほぼ快晴、
0.42は青空を主体に独立した積雲を残した。このため新規プロジェクトの晴天既定値を0.50から0.42へ
変更する。既存プロジェクトが`CloudCoverage=0.50`以上を明示している場合は変更せず、多雲または曇天の
設定として扱う。

雲量だけで雲種や降水域まで暗黙に決めないよう、`FVolumetricCloudWeather`を追加した。
`CloudType`は層雲から積雲までの高さ形状、`Precipitation`は降水成分を表し、それぞれの適用率で
手続き生成した模様を残す量を決める。GPUでは被覆の時間変化より前に適用し、視線密度、自己影、
立体物へ落とす雲影が同じ値を使う。既定の適用率は0であり、既存の密度場と負荷を変更しない。
雲種または降水成分が高い領域では、雲柱の高さ変動・雲底の局所的な持ち上げ・雲頂側のかなとこを
追加する。積乱雲本体は中層の厚みを連続して保ちながら上側を少し絞り、かなとこを別の密度の山として
接続する。雲柱の上下変形量は雲層全体を引き伸ばさない範囲へ制限し、かなとこは上部の被覆しきい値だけを下げて横へ広げるため、
同じ天候採取結果を視線・光採取・雲影で共有する。物理的な積乱雲の高さは`BaseAltitude`と
`TopAltitude`の差で決まり、2.6 kmの下層を設定したままでは高い積乱雲にはならない。
雲底の局所持ち上げ振幅は通常雲の`0.025`から対流雲の`0.045`へ増やす一方、積乱雲では
共通の凝結高度へ底面が揃いやすい性質に合わせて`0.80`倍へ抑える。低周波信号を含む実際の
最大持ち上げ量は正規化高度`0.0175`～`0.0252`であり、9.4 kmの雲層では約165～237 mとなる。
従来の積乱雲最大`0.113925`、同じ層で約1.07 kmは雲頂変形と逆向きに長い下向きの尾を作るため
廃止した。雲頂側は最大約1.4 kmの高さ変形を独立して維持し、上層雲では雲底係数を`0.35`倍にして
薄い層を分断しない。
雲底密度も層厚の固定比率ではなく、物理距離を基準に立ち上げる。層雲・層積雲・積雲は
2.6 km層で意図していた約143・234・338 mを保ち、9.4 km層でも同じ約143・234・338 mに収める。
固定比率では同じ9.4 km層で約517・846・1,222 mまで広がり、3D形状の高密度な中心だけが
長い下向きの筋として残っていた。積乱雲本体はさらに鋭い約120 mを基準とし、9.4 km層でも
約122 mに収める。各終端の上下限は極端な薄層を雲底だけで埋めず、厚層で再び長い垂れを
作らないために使う。
基本形状の高さ方向領域は固定倍率でなく、`層厚×横方向形状尺度`から求める。9.4 km層と
`CloudNoiseScale=0.035`では高さ領域を約`1.974`周期幅とし、横方向の約2.38 km級の
低周波形状を高さ方向へ約3 km以上引き伸ばさない。値は`1.20～2.20`へ収め、薄い層が
単一断面へ潰れることと、厚い層が細かな数珠状へ分断されることを同時に避ける。
さらに中層では完成マスクを薄くするだけでなく、天候場の被覆しきい値を最大`0.010`上げて
正の領域そのものを内側へ閉じる。これにより低密度の輪郭が雲底から雲頂まで同じ幅で残る
柱を避ける。上部のかなとこ被覆はこのくびれとは別に残すため、積乱雲の上部だけが再び
横へ広がる。ただし、かなとこ側のしきい値低下は天候遷移幅`0.14`を越えない`0.070`へ
制限し、本体より極端に広い雲蓋から細い柱が垂れて見える状態を避ける。
かなとこ拡張量が0の高さでは未補正被覆とくびれ後被覆を`max`しない。両者は
同じ被覆になるため、その処理順では中層のくびれが常に消えていた。拡張量を0～1の混合率へ
直して、雲底と中層では細い本体を保ち、かなとこ帯だけを拡張後の被覆へ連続的に戻す。
雲底付近では高度`0.04`～`0.26`へ低密度の端を面へ寄せる締め処理を全描画経路へ適用する。
通常雲では最大`16%`、積乱雲では最大`40%`だけ密度を二乗側へ寄せ、密度の高い雲底を残したまま
細い垂れだけを抑える。中層まで密度を二乗側へ寄せると、本体だけが細くなって広いかなとこから
柱が垂れるため適用しない。中層の幅は3D基本形状と被覆しきい値で決め、かなとこ帯の薄い縁と
上部の横張り出しは変更しない。
3D形状テクスチャは低周波を主形状にしたR成分へ中周波を少量混ぜ、焼き込み済みPerlin–WorleyのG成分も
`0.18`～`0.70`の実分布で近景の立体的な侵食へ使う。最大侵食率は従来の`14%`～`26%`を
維持して雲体の連結性を崩さない。高さ軸は正規化高度へ`1.55`倍で写像し、9.4 km級の雲層でも
高さ方向の低周波形状が一度の雲塔として連続しながら変化するようにする。従来の`2.75`倍では
低周波形状が層内で繰り返され、中層から雲底へ細い垂れが連続して見えることがあった。視線側と
光採取側は同じ係数を使い、形状だけが高さ方向へ引き伸ばされる不整合を避ける。
さらに天候場の高さ方向のずれを厚い雲層で約1.5～2.5 kmへ広げ、同じ被覆をそのまま
押し出さないようにする。薄い2.6 km級の雲層では増幅を0.45倍へ抑え、雲底・中層・雲頂で
雲塊の位置が連続して変わるため、上空視点で雲塊が一枚の平面へ潰れず、雲中視点でも前後の
密度差を保てる。
等倍追跡では全画素が現在フレームの実レイを持つため、時間履歴の色混合を行わず、現在値と
現在深度をそのまま表示する。過去色を混ぜると、積乱雲の細い柱やかなとこの縁が前フレームへ
引かれて密度形状より柔らかくなる。低解像度追跡だけが、現在フレームの標本を持たない画素へ
時間再構成を使う。
通常C++では`CVolumetricClouds::SetWeather()`、従来の3Dアダプターでは`FScene3DClouds::Weather`から
同じ経路を使う。各値は有限な0～1へ正規化し、変更時は密度・時間履歴と両方の雲影を無効化する。

雲量0.50の通常品質を20秒計測したところ、雲種0.78へ68%寄せて降水成分を0へ固定する設定は、
地平線平均3.38 ms、天頂平均2.79 msだった。見た目の差が小さい一方で、適用率0の同一バイナリは
地平線平均2.59 ms、天頂平均1.56 msであったため、前者を晴天既定には採用しない。適用率0の計測は
両視点とも品質判定を通過し、最大視線採取数、最大光採取数、時間再構成、影更新量は規定値と一致した。
雲種固定は作品または天候プリセットが意図して選び、増えた占有領域を含めて性能確認する。

`90428AEDDBC05CBB7621C4D470F83C78E651C5D3DBA588AA12F6DB6D3A268E52`でも再計測し、
地平線は平均3.04 ms・最大3.79 ms、天頂は平均1.54 ms・最大2.17 msだった。両視点の品質判定と

### 天候遷移の連続性監査

既存の`CWeatherSystem`は遷移中に別の天候を指定すると、補間途中の描画係数を捨てて旧目標を新しい
開始天候にしていた。たとえば快晴から豪雨へ50%進んだ時点で曇りへ変更すると、環境光、粒子、空色、
風、霧が豪雨100%へ1フレームで跳んでから曇りへ戻る。これは天候名が離散値であることを理由にした
近似ではなく、遷移の処理順による不連続である。

現在は5成分の開始値を連続値として保持し、各成分を`P = P_start + (P_target - P_start) * t`で補間する。
目標変更時は目標を書き換える前に現在の`P`を全成分で求め、次の`P_start`へ保存してから`t=0`へ戻す。
同じ目標を正の時間で再指定した場合は経過時間を維持し、0以下または非有限の遷移時間は即時切替する。
`Tick`は0以下と非数の経過時間を無視し、残り時間以上かを加算前に判定するため、加算あふれから非数を
作らない。範囲外の`EWeatherKind`は保存前に`Clear`へ直す。

専用試験は、全5成分が同じ進行度を使うこと、途中の目標変更で値が連続すること、同一目標の再指定、
非数と正の無限大相当の時間、範囲外種別を検査した。Releaseは1410件、Debugは1414件が全合格し、
Editor ABIも両構成でビルドできた。内部処理はprivateの`Params_Internal`、
`NormalizeKind_Internal`、`CurrentParams_Internal`、`CompleteTransition_Internal`へ閉じ、`friend`やSTLは
追加していない。

`291dc4eb`のソースからDebug・Release配布物を隔離生成し、44件の実体ファイルとmanifestの計45件を
生成元と配置先で照合した。manifestのSHA-256は
`5975EEDB1884A7AC6FA13D2D06BB8DE732DA6DFBD21E293161E7809CBFD612D2`、単一ヘッダーは
`781999C83582DF1BD88C284F06D387C22C480F7E6E47597CAFAB214A532122AD`、正規consumer契約は
`A8DA14318DBE49DF965A49ABB99C64461D16207515645223F0330961369A61B4`だった。

正規consumer契約は`CWeatherSystem`を配布headerから生成し、快晴から豪雨への途中で曇りへ目標変更する。

## 雲形状の帯域制御と照明単位の監査

雲量0.42の参照描画を地上から確認したところ、細かな3D模様は減っていたが、低周波形状が直立した柱と
白く飽和した直方体に見えた。原因は一つではない。2D被覆の細かな周波数を層全高へ押し出していたこと、
高さ分布を`smoothstep(0.02, 0.32, profile)`で早期に飽和させて層中央の大半を同じ太さにしていたこと、
視線刻みより細かな基本形状と侵食を遠景でも採取していたこと、雲だけが正規化済みHG位相関数へ
`4PI`を掛けてPBR主光源より`PI`倍明るくなっていたことを分離して修正した。

被覆生成は雲塊配置用の3・7周波数段だけを使い、層内高さに応じて総観規模と地域規模を別方向へ
緩やかに曲げる。基本形状体積は低周波形状と全帯域形状をRGへ保持し、レイ採取間隔から解像できる
帯域と変換領域だけを補間・採取する。約0.8～1.8 kmの房と約0.2～0.45 kmの侵食も別々の採取限界で
減衰させた。高さ分布は飽和させず`profile * sqrt(profile)`を底面から雲頂まで適用し、中心の1を保った
まま上下端を連続して絞る。この時点ではPBRのLambert面と明るさを合わせるため、
`1/(4PI)`を含むHGを4倍していた。後続の「雲照明の物理式と積分順序の再監査」で、
面反射の`1/PI`を体積散乱へ流用した誤りと判明し、現在は正規化HGを倍率なしで使う。

参照描画は次の三視点で確認した。地上視点`--camera3d 0 -0.08 18 0 2 0`では青空の抜けを保ち、
白潰れの中へ消えていた房の陰影が読めるようになった。雲層高度の横視点
`--camera3d 0 0.02 5000 0 4300 0`では直立した板ではなく前後に分離した雲塊を確認した。上空視点
`--camera3d 0 0.35 8000 0 7200 0`では雲頂に独立した房と空隙があり、2D被覆を押し出した面は
見えなかった。ただし雲頂の細かな侵食はまだ柔らかく、UE級の完成とは扱わない。次の品質ループは
上空で読める中周波の房と、時間変化してもちらつかない表面侵食を対象にする。

manifestのSHA-256は`3CFCF90047B94D9F4FF0C00CD74A13A424A12A01AA66EA2B244130BE07312284`だった。

## 雲頂の中間帯域と詳細LODの監査

詳細体積のR成分は4周波数のWorley形状、G成分は4・16・64周波数を`0.55 : 0.30 : 0.15`で混合した
形状を保持している。従来の雲頂変形はR成分だけを使い、G成分は密度を内側へ削る処理にしか使って
いなかった。このため、大きな房と細かな侵食の間をつなぐ中間規模の膨らみがなく、上空から見た輪郭が
滑らかな塊へ寄っていた。

現在は追加の体積テクスチャ採取やメモリを増やさず、`(G - 0.55 * R) / 0.45`から16・64周波数の
中間帯域を復元する。雲頂側の高さ0.38から0.90に限って最大0.48の比率で粗い房へ混ぜ、雲底の平坦さと
層全体の連続性は維持する。粗帯域と中間帯域の差分を凸結合するため、既存の最大変位量は厳密な占有範囲の
上限として引き続き使える。

詳細LODは手作業の距離判定をやめ、最も細かな詳細領域の実周波数から求めた画素足跡
`sampleSpacing * 0.00031 * frequency`で判定する。4周波数の粗い房は採取間隔約121 mから減衰し、
約419 mで停止する。16周波数以上の中間帯域と侵食は約10 mから減衰し、約48.4 mで停止する。
これにより、1回のレイ採取で半周期も解像できない模様を評価してちらつきへ変える処理を避ける。

雲量0.42の同一場面を地上、雲層高度、上空から再確認した。上空では大きな雲塊の輪郭へ中規模の房が
加わり、空隙と独立した塊を保った。地上では青空の抜けを維持し、雲層高度では8秒待機後も柱状化や
明白なちらつきはなかった。ただし輪郭にはまだ拡大復元由来と考えられる柔らかさと角張りが残るため、
完成とは扱わない。次の品質ループでは、現在の低解像度トレースと時間・空間復元を監査する。

## 基本形状の実分布と雲体連結性の監査

雲量`0.42`の基準描画は`CloudRenderScale=1.0`、`CloudReferenceMode=true`であり、全画素を最大512段、
時間再構成なしで追跡している。同じ粒状・綿状の形がこの経路にも残ったため、今回の主因を低解像度の
拡大復元とは扱わない。密度式をCPUで同じ決定的ハッシュ、Perlin、Worley、合成順に再現し、
131072個の一様な3次元座標を測った。低周波成分は平均`0.668839`、標準偏差`0.054308`、
全帯域成分は平均`0.669200`、標準偏差`0.045649`だった。

従来の第2〜第4領域は、採取値から`0.5`を引けば平均0になると仮定し、重み
`0.30 : 0.18 : 0.10`で雲体へ直接加えていた。実分布では合計約`0.098`の正の偏りとなり、
独立した細かな領域が雲体を常に膨らませていた。0〜1の一様値を列挙した旧試験はこの偏りを検出できず、
実装コメントの「平均0」も成立していなかった。

現在は第1領域を雲体として保ち、全帯域との差は近景でも28%だけ混ぜる。独立領域の重みは視線側を
`0.16 : 0.07 : 0.03`、光路側を`0.16 : 0.07`とし、各値から実分布中心`0.67`を引いてから加える。
未採取領域の正方向上限も`0.5 * weight`ではなく`0.33 * weight`へ直した。視線側の全未採取領域が
追加できる最大量は`0.0858`で、基本密度の遷移幅`0.22`より小さい。全入力を列挙する単体試験で、
段階的な空間棄却が後からしきい値を越える密度を捨てないことを確認する。テクスチャ採取数、
体積解像度、GPU資源は増やしていない。

偏りを除くだけでは雲量が減り、雲頂と雲底の薄い高さでは主形状の上側だけが小島として残る。
そこで既に求めた低周波の天候中心度`m`と変形後高度`h`から、次のしきい値低下量を求める。

`o = smoothstep(0.18, 0.82, m) * smoothstep(0.10, 0.30, h)`

`    * (1 - smoothstep(0.82, 0.98, h)) * (upperBand ? 0.025 : 0.080)`

空間占有、視線密度、近距離光、遠距離光の形状しきい値から同じ`o`を引く。天候中心では低周波の
主形状を連結し、天候縁では従来の3次元侵食を保つ。雲底と雲頂では`o=0`へ戻るため、2D天候場を
層全体へ押し出した板にはしない。占有用被覆は密度用被覆以上なので、この補正後も占有しきい値は
詳細密度より緩く、保守的な省略条件を維持する。

柱の高さ変形も再監査し、正規化高度`0.14`までは恒等変換として雲底を固定した。その上では
`16u²(1-u)²`を使い、凝結高度と雲頂で値と傾きを連続させながら、中央の最大成長量と全許容範囲での
単調性を保つ。以前の式が雲底寄りでも柱ごとの差を残すことを正しいとした試験は削除し、
雲底固定、値域、単調性、視線と光路の式一致を検査する試験へ置き換えた。

雲種と降水を積雲・無降水へ固定した比較、および通常の手続き型天候を、地上、雲層高度、上空から
全解像度で確認した。細かな独立領域が作っていた小粒の集合は減り、低周波の雲体と青空の空隙を
同時に保った。ただし大きな房の表面はまだ柔らかく、暗い雲底と縦長の隆起が綿や煙に見える場面がある。
この修正を雲表現の完成とは扱わない。次の品質ループは、雲体を再び細分化せずに房の曲率を読ませる

## Perlin-Worley分布、可変雲頂、拡散照明の再監査

前節の中心補正は、焼き込み式そのものが正しいという仮定を残していた。Guerrilla Gamesの一次資料にある
Perlin-Worleyは`remap(perlin, 1 - worley, 1, 0, 1)`である。ACSの`worley`は既に
`1 - 最近接距離`を返しているため、従来の下限`worley - 1`は符号が逆だった。正しい式へ直した全帯域値は
平均`0.073072`、標準偏差`0.110955`、中央値`0`、90百分位`0.254349`、99百分位`0.410231`、
最大`0.654489`となり、雲体の中心値として使える分布ではなかった。

そこでR成分は`0.58 * Perlin2 + 0.30 * Perlin4 + 0.12 * Perlin8`の連続した主形状へ分離した。
低周波を68%残すため雲塊の連結性は維持しつつ、中周波を12%だけ加えて同じ高さへ伸びる縦筋を
横方向へ分散させる。`Perlin8`は焼き込み時に既に計算しているため、テクスチャ採取回数と容量は増えない。
G成分には正しいPerlin-Worleyを保持し、主形状を増やさない乗算侵食だけへ使う。追加の三領域も
同じ規則で最大`0.04`、`0.02`、`0.01`だけ侵食する。
雲頂では第1領域の最大侵食を`0.14`から`0.26`へ増やしたが、全領域が最大侵食でも主形状の
約68.9%を残す。全65536入力の列挙試験で、空の支持範囲を新たに雲へ変えないこと、段階棄却後に
しきい値を回復しないことを確認した。

二領域を混ぜた天候被覆は平均`0.545074`、標準偏差`0.110033`だった。しきい値を
`0.72 - 0.36 * coverage`へ直すと、正の被覆面積は入力`0.10`、`0.25`、`0.42`、`0.50`、
`0.75`、`0.90`に対して約9.56%、22.20%、42.17%、52.41%、79.84%、90.17%となる。
GPU式だけを変更しても、通常経路はCPUで事前計算した旧しきい値を定数バッファから使っていた。
天候しきい値と高さしきい値の両方をCPU/GPUで同じ式へ揃え、GPU側だけを直したのに画面が変わらない
処理順の不整合を除いた。主形状の実範囲に合わせ、高さ中央のしきい値は雲量に応じて`0.50`から
`0.34`へ変える。

高さ分布は雲体内部の低密度を平方根で満たし、雲底・雲頂の端では密度を二乗側へ戻してから、
生の高さ形状を完成密度へ掛ける。端の補間は高さ形状`0.35`～`0.78`で切り替え、低密度の細部だけが
長い垂れへ変わるのを抑える。さらに支持量は`0.10`～`0.56`で低い高さだけ二乗側へ寄せ、雲頂の高さ、
中心の密度1、かなとこの厚い部分は変えない。積乱雲本体の立ち上がりも高さ形状`0.06`～`0.22`へ
広げ、肩の始まりを`0.24`～`0.36`へ移して、雲底の細い縦柱だけを丸める。雲頂変形は従来の

## 雲表面と雲芯が同じ位相混合を使っていた問題の修正

従来の単一散乱は、前方と後方のHenyey-Greenstein位相をレイごとに固定率で混ぜていた。
光源方向の光学的深さが増えると直接光量は減るが、薄い雲縁と遮光された雲芯の散乱方向は
同じままだった。このため、雲層内の長い視線では自己影が付いても大きな房の中間色が近づき、
局所的な濃淡を持たない灰色へ寄りやすかった。

現在は前方位相`p_f`と後方位相`p_b`をレイごとに一度だけ求め、各密度標本では次の式で混合する。

`w_f = saturate(PhaseBlend) * T_light * T_interval`

`phase = clamp(lerp(p_b, p_f, w_f), PhaseMin, PhaseMax)`

`T_light`は光源までの透過率、`T_interval`は現在の視線区間の透過率である。両方が1の薄い表面では
従来の作者指定混合と一致し、自己影または現在区間の密度が増えるほど前方散乱を弱めて後方散乱へ
連続的に移す。これはGhost of Tsushimaで示された、雲の深さを二つの透過率の積で近似する方法を
ACSの既存の前方・後方位相へ適用したものである。多重散乱は既存の二次・三次近似で別に扱うため、
後方位相へ公開資料の輝度倍率を重ねて二重計上していない。現在区間の透過率は不透明度積分にも
再利用し、標本ごとの追加`pow`、光採取、texture、状態、公開APIは増やしていない。

## 雲中の下向き視線を地平線除外で消していた問題の修正

雲中カメラでは、視線積分の開始点を`0`へ戻していても、地面の地平線より下を先に空間除外する
処理が残っていた。これでは下向き視線のカメラ直前に雲がある場合でも、雲へ到達する前に画素を

## 雲中環境光が現在地点の密度だけを見ていた問題の修正

以前の環境光は、現在地点の低詳細度密度と層境界までの正規化距離だけで空側と地面側の遮蔽を
近似していた。同じ局所密度なら、頭上に空への抜けがある房と、その上に厚い雲芯が続く房を
区別できない。このため、直接光と多重散乱に差があっても中間層の環境光が近い値へ寄り、広い
灰色面として見えやすかった。

現在は動的自己遮蔽キャッシュを `RGBA16F` にし、太陽方向の平均深さと二標本差に加えて、各XZ列の
空・地面方向の積算密度を保持する。キャッシュの一つのGPUスレッドは同じ列の32高度を下から順に
評価する。層厚を `H`、粗密度を `d_i` とすると一セルの深さは次式になる。

`delta_i = max(d_i, 0) * (H / 32) * (1.6 / H) = max(d_i, 0) * 1.6 / 32`

各セル中心では現在セルの半分を上下へ分け、`tau_sky + tau_ground = sum(delta_i)` を必ず保つ。
これにより高度ごとに上下へ別々のレイを積分せず、列当たり32回の粗密度評価で全高度の値を得る。
シェーダーは `[numthreads(4,1,4)]` とし、安定時の論理出力 `48 x 32 x 48 = 73728` に対して
起動スレッド数は `48 x 48 = 2304` である。管理側Editorと計測スクリプトも
`起動数 x 32 = 論理出力数` の完全一致を要求し、不足だけでなく余分な列も契約違反として拒否する。

視線積分では、キャッシュ内なら積算密度へ作者指定密度と距離減衰を掛け、範囲外と上層雲では従来の
局所近似へ滑らかに戻す。さらにNubisの環境散乱確率に合わせ、降水・高度の増密を掛ける前の
形状勾配を`d_profile`として、表面確率を
`P_surface = sqrt(saturate(1 - d_profile))` とし、空・地面それぞれの可視率を
`P_surface * exp(-sigma_reduced * tau)` とする。これは垂直二方向の近似であり、半球全体を追跡する
経路追跡やGIそのものではない。追加した積算密度は「局所密度が同じなら同じ明るさ」という不整合を
除くために使い、直接光、位相関数、視線標本数は変えていない。

初期実装は`d_profile`の代わりに、雲底側の1.10倍、降水増密、距離減衰を含む最終低詳細度密度を
使っていた。雲底では倍率後に1へ飽和して表面確率が0となる一方、描画終端では距離減衰により同じ形状が
明るくなり、晴天積雲の暗部と遠端の光輪を同時に作る不整合だった。現在は同じ基本形状採取から倍率前の
勾配を併記し、追加のテクスチャ採取なしで一次資料の変数と処理順へ合わせている。

たとえば`d_profile=0.9`、降水0では、旧式の表面確率は雲底側の1.10倍で`0.10`、雲頂側の0.92倍で

高度と降水による実際の厚み差は上下積算密度の指数減衰へ残し、形状表面の確率へ二重適用しない。

## 太陽方向の第4標本だけが房状自己影を失っていた問題の修正

上面が柔らかい白い面へ寄る原因を時間再構成と密度・照明に分けるため、同じ雲設定と上面カメラで
通常描画と参照描画を比較した。参照描画は全画面解像度、視線上限512標本、時間再構成なしである。

既定の2500 m層では、太陽方向の最初の刻みは決定論的な採取位相により`8.44～15.00 m`となり、標本ごとに
1.8倍へ広がる。最初の3標本の後に来る第4区間は`49.21～87.48 m`である。この間隔では

格子状の別名雑音を作るため、従来の低詳細度基準だけを保持する。主描画側で現在画素の差分を重ねることで、

## 上空視点で雲頂が灰色へ潰れていた問題の修正

通常のC++経路で上空カメラから撮影すると、地平線視点では見えない灰色の平坦化が雲頂に残った。
上空では太陽方向と視線方向が逆向きになるため、前方散乱と既存の二・三次散乱だけでは、雲頂の
細かな水滴群が返す拡散光を十分に表現できない。これを雲全体の色や大気の曇天度で補正すると、
雲底と地平線側まで白くなるため採用しない。

位相角は視線方向の符号を含めて評価する。`dir`はカメラから雲へ向かう入射レイなので、
標本からカメラへ出る方向は`-dir`である。したがって太陽方向を`sun`とすると、比較する角度は
`cosA = clamp(dot(-dir, sun), -1, 1)`となる。この値を前方・後方のHenyey--Greenstein位相へ
渡し、一次散乱は現在の密度と区間不透明度、高次散乱は周囲散乱源の確率でそれぞれ制限する。
以前の`dot(dir, sun)`は上空視点で出射方向を逆に扱い、太陽側の雲頂を暗くし得るため修正した。
この修正は既存の採取数や散乱次数を増やさず、雲頂へ任意の色や追加エネルギーを足すものでもない。
GIや半球経路追跡を実装したことを意味せず、雲中の房状の濃淡と包囲感は別の品質課題として残る。
単体試験では正しい`-dir`の式を固定し、旧符号が再導入されないことを検査する。

## 雲照明の物理式と積分順序の再監査

既存実装を一次資料と均質媒質の解析解へ照合したところ、見た目の補正で互いに隠れていた五つの
不整合が見つかった。

- 全立体角で1へ正規化済みのHenyey-Greenstein位相へ4を掛け、積分値を4へ増幅していた。
- 異方性`g=0.99`を許可しながら分母の底を`1e-3`へ丸め、位相積分を約`0.456`へ欠落させていた。
- 作者指定の前方・後方混合率へ現在の視線区間透過率を掛け、刻み幅で単一散乱の物性が変わっていた。
- 二次・三次散乱は光源側だけ消散を弱め、視線側では一次散乱の区間重みと累積透過率を再利用していた。
- 光路の早期終了を一次散乱の光学的深さだけで決め、まだ残る高次散乱の光を途中で切っていた。

位相は`1/(4PI)`を含む正規化HGを倍率なしで使う。CPUが`abs(g) <= 0.99`を保証するため、分母の底は
理論上`1e-4`以上である。鋭い前方・後方ピークでは近い数同士を引かず、異方性の符号に応じて
`(1-abs(g))^2`へ非負項を足す等価式を使い、単精度の桁落ちも避ける。GPU側の`1e-6`は丸め誤差だけを
防ぐ。前方・後方を固定の`PhaseBlend`で混ぜる。
Frostbiteの近似と同様に、次数`n`の散乱係数を`a^n`、消散係数を`b^n`へ縮小する。光学的深さ
`tau`の視線区間が持つ次数別の解析重みは次式になる。

`W_n = (a^n / b^n) * (1 - exp(-tau * b^n))`

各次数は専用の累積視線透過率へ`exp(-tau*b^n)`を掛け、光源側にも同じ`b^n`を適用する。
`b`が0へ近づく場合は`a^n*tau`の極限を使い、CPU設定では`0 <= a <= b <= 1`を保証する。
雲頂だけへ`0.22`の方向項を足していた上面拡散補正は、正規化されず高次散乱を二重計上するため削除した。
上空からの明るさと厚みは、同じ二次・三次の体積輸送で得る。

光学的深さ5、既定`a=b=0.28`では、旧視線重みは二次`0.2781`、三次`0.0779`だった。
次数別に正しく積分すると二次`0.7534`、三次`0.3243`となり、厚い媒質で失われていた回り込みを
復元できる。一方、光学的深さ`0.001`では新旧差が`1e-7`程度に収まり、薄い雲縁の一次精度は保つ。
1、2、7、64、257区間へ分割した数値積分が同じ解析解へ一致する試験、HGと二ローブ混合の球面積分が
1へ一致する試験、最高次数を考慮した光路終了試験を追加した。根拠はFrostbiteの
[SIGGRAPH 2016講義資料](https://media.contentapi.ea.com/content/dam/eacom/frostbite/files/s2016-pbs-frostbite-sky-clouds-new.pdf)、
Guerrillaの[Nubis Evolved 2022講義資料](https://advances.realtimerendering.com/s2022/SIGGRAPH2022-Advances-NubisEvolved-NoVideos.pdf)
および[Nubis Cubed 2023講義資料](https://d3d3g8mu99pzk9.cloudfront.net/AndrewSchneider/Nubis%20Cubed.pdf)である。

## 密度生成・高さ座標・空間棄却の再監査

既存の密度式を、見た目や既存試験ではなく一次資料の式と数値分布へ照合した。Nubis 2017の
Perlin-Worley生成式は`remap(perlin, 1 - worley, 1, 0, 1)`、低周波形状と侵食形状の合成は
`remap(low_freq_noise, high_freq_noise, 1, 0, 1)`である。ACSの`worley`は最近接距離を反転して返すため、
`1 - worleyFull`を最初の下限に使う現在の向きは意図どおりである。Hillaireの公開生成器には
`remap(perlin, 0, 1, worleyFbm, 1)`という別案もあり、同ソース自身が資料本文と画像の差、調整係数の
多さを明記している。名称だけを根拠に二つの式を入れ替えない。

Nubis Evolved 2022の密度式は、まず`dimensional_profile = vertical_profile * cloud_coverage`を作り、
次に`cloud_density = saturate(cloud_noise_composite - (1 - dimensional_profile))`を一度だけ適用する。
旧ACSは、雲量で基本雑音のしきい値を動かした後に高さ分布と被覆を再適用しており、低い雲量ほど
基本雑音の上端だけが残る二重適用になっていた。現在は、基本雑音を固定範囲で正規化し、縦分布と
2D被覆の積を一度だけ差し引く。完成密度が正になり得る生雑音下限は、その式を逆算した
`upper + (lower - upper) * dimensional_profile`で求める。

固定範囲は見た目合わせではなく、128立方の実シェーダー生成式と三線形採取をCPUで再現して確認した。
乱数種`20260826`、連続座標20万点、三つの追加形状領域を通した分布は、1百分位`0.259342`、
中央値`0.347588`、99百分位`0.527812`だった。使用範囲`0.25～0.54`は両端を少し外側へ残す。
同じ監査で次の不整合も修正した。

- 未解像の追加形状を「侵食なし」へ戻すと遠距離ほど平均密度が増えるため、実測した侵食信号平均
  `0.232`へ収束させた。
- 3D詳細座標へ接平面の世界Yを使うと、同じ球殻高度でも原点から100 km離れた位置で約786 mの
  位相差が混入する。球殻高度を使い、主形状の軸外しも長さを保つ直交回転へ直した。
- 太陽光路の別地点へ視線地点の天候、局所雲頂、渦を流用すると、雲縁を越えて同じ密度柱が延びる。
  近距離・遠距離とも採取地点ごとに密度条件を再構成する。
- 全球層上端を全柱の雲頂にせず、局所雲底と局所雲頂の間だけを単調に0～1へ写す。積乱雲本体、肩、
  かなとこを独立した山の最大値にしていた中層の谷も、連続した本体とかなとこへ直した。
- 空間棄却は形状の固定値ではなく、高度、降水、作者密度、上層密度を含む完成密度上限が
  `0.0015`以下の場合だけ行う。後段の倍率で可視になる薄い縁を先に捨てない。

## 層厚と光学的深さの物理単位再監査

2026-08-26の再監査では、既存試験が「一様密度ならどの層厚でも総光学的深さが`1.6`になる」ことを
合格条件としており、実装の誤った正規化をそのまま保証していた。消散係数の単位は`m^-1`、光学的深さは
経路上の消散係数の距離積分、透過率はBeer-Lambert則`T = exp(-tau)`である。したがって、同じ密度の
媒質を長く通過するほど`tau`が増えなければならない。

基準消散係数は、厚さ2500 mの既定層で従来値を保つ`1.6 / 2500 = 0.00064 m^-1`とした。独立数値試験では、
一様密度1、作者密度1、消散倍率1の900 m、2500 m、9400 m経路が、それぞれ`tau = 0.576`、`1.6`、
`6.016`になること、9400 mと2500 mの比が距離比`9400 / 2500`へ一致すること、各透過率が距離に対して
単調に減ることを確認する。太陽光の採取間隔は層厚に比例して標本範囲を保つ品質上の尺度であり、物理消散とは
分離した。視線、近距離と遠距離の太陽光、動的自己遮蔽キャッシュ、3D受光面用ワールド雲影の全経路が、
標本地点の上下層を判定しながら同じ`m^-1`係数で実距離を積分する。

根拠はFrostbiteの
[SIGGRAPH 2016講義資料](https://media.contentapi.ea.com/content/dam/eacom/frostbite/files/s2016-pbs-frostbite-sky-clouds-new.pdf)にある
消散係数、光学的深さ、区間散乱の定義である。同資料が示す実水雲の消散係数はさらに大きいが、ACSの密度場は
物理的な液水量そのものではないため、今回の係数は既定の見た目を保つ基準値として扱い、単位と距離依存だけを
正した。

Debug単体試験`1524 / 1524`、Release単体試験`1520 / 1520`、Visual Studio正規出力とNinja出力の
Debug・Release全体生成、Editor ABI、管理側Editorの両構成に合格した。管理側Editorは警告0・エラー0である。
配布工程の自己試験後、Debug・Releaseを含む45ファイル、`1,256,955,857`バイトを既定の隔離配布先へ配置した。
検査表`acs-distribution.sha256`のSHA-256は
`159748B7D80ABAB1B428544A271B43C74D46C3E7DEB57F7D096D4B60A769B2FB`、`acs.h`は
`0C9D6E95BC1A6A13EAEDF86763A31F2959C28BFFEEB7D39F5C6D82D1309E0FA9`である。配布ツリーだけを参照する
通常C++利用者は両構成でコンパイル、リンク、実行に合格した。ACS Framework正本
`f1ca4985a84ffa29d101b7bdaae9d31d85b7cf9a`も同じ配布先を`AcsDistRoot`へ明示し、ソースを変更せず
Debug・Releaseの全体ビルドに合格した。

実画面では地上から雲の高さと厚みが明確になった一方、縦長の暗い煙状となった。雲中は灰色の壁と粒状感が強く、
上空は青灰色で白い受光面が不足する。物理消散を層厚で相殺して明るく戻すのは採用せず、この三視点を照明輸送の
不合格証拠として残す。次は太陽照度、周囲光、多重散乱の単位と適用順を独立に監査する。

## 単散乱アルベドと有限次数補償の適用順再監査

2026-08-26の再監査では、`SunScatter`を単散乱アルベドと説明しながら太陽光にしか掛けず、空半球と
地面側から入る光はアルベド1として積分していた。同じ媒質の吸収率が光源の種類で変わるため不整合である。
現在は、視線区間の消散で得た不透明度へ太陽、空、地面の各入射光を加える前に、全項へ同じ
`0 <= SunScatter <= 1`を適用する。値0の吸収媒質では補償倍率が有限でも散乱光が0になることを独立数値試験で
確認する。

正規化したHenyey-Greenstein位相は全立体角の積分が1であり、見た目の明るさを位相へ混ぜない。一方、
三次までの多重散乱近似はそれより高い次数の光を捨てるため、太陽から入る有向光に限って
`SunScatteringLuminanceScale`を最後に掛ける。範囲は`0～16`で、補償なしの既定値は`1.0`である。
近似で失う量は密度、光学的深さ、散乱次数、視線で変わり、一律`4.0`を導く式はない。さらに`4.0`は、
正規化修正前にLambert面の`1/PI`を体積散乱へ誤用していた位相4倍と数値的に同じである。見た目が戻るだけの
一致を物理既定の根拠にせず、4倍の既定値は不採用とした。補償自体はアルベドや位相の正規化を変えず、一次、
二次、三次の合計輝度を同率で調整する。CPU参照式とGPU式は同じ積とし、
`SunScatter=0.25`、補償`3.0`なら補償なし・アルベド1の結果の正確に`0.75`倍になることを検査する。
この分離はUnreal Engineの
[Cloud Scattering Luminance Scale](https://dev.epicgames.com/documentation/en-us/unreal-engine/volumetric-cloud-component-properties-in-unreal-engine)
と同じ目的であり、完全な多重散乱解を主張するものではない。

Editorでは`CloudSunScatteringLuminanceScale`、通常C++では
`Clouds().Lighting.SunScatteringLuminanceScale`から同じ補償値を指定できる。比較用の検証シーンだけは
両経路で`4.0`を明示し、既定の物理条件と、近似誤差を含む見た目の調整条件を分離した。

通常C++経路は現在の空の地面側放射輝度を雲へ渡しておらず、Editor経路と同じ設定でも雲底の色が異なっていた。
`ALegacyScene3DAdapter`も毎フレーム`CSky::GroundColor()`を渡し、画面描画と環境cubemapの両方で同じ照明を使う。
新しい補償値は`FVolumetricCloudLighting`内で後続の16バイト型の手前にあった4バイト余白へ置いた。
初回の構造体末尾への追加では固定配置試験6件が実際に失敗したため採用せず、公開構造体の大きさと後続要素の
位置を維持した配置だけを採用した。

通常C++検証シーンにも誤りがあった。`SetOrbit`へ`2500～18000 m`を渡していたが、カメラ制御側は距離を
最大`200 m`へ制限する。そのため従来の地上、雲中、上空という表示名に反して、実カメラは全て雲層付近にいた。
距離`200 m`から目標点を逆算し、実カメラ高度を約`50 m`、`6200 m`、`13000 m`へ分けた。さらに
`ACS_CLOUD_AUDIT_VIEW=ground|inside|above`で一回の起動を一視点へ固定し、時間切り替えの成否を
視覚証拠へ混ぜないようにした。

さらに、通常C++検証は被覆`0.32`、密度`1.6`、雲種と降水の部分適用、等倍描画である一方、Editorは被覆
`0.42`、密度`2.1`、雲種`1.0`と降水`0.85`の全適用、内部基準倍率`1.0`、約3倍明るい太陽だった。
この状態の画面差は描画経路差を証明しない。検証用プロジェクト`27279a6`で両経路の天候、描画倍率、太陽強度を
そろえ、同じ目標点、向き、距離でも再撮影した。

同一入力後の通常C++実画面では、地上から青空と明るい受光面を保ち、上空でも補償による白飛びは起きなかった。
ただし地上は縦長の灰色の煙状部分と粒状の自己影が残る。雲中は地平線と背景が広く見え、縦の半透明塊しかなく、

## 雲の時間再構成における画素履歴の再監査

2026-08-26の再監査では、4×4時間再構成の未採取画素へ、別の等倍レイから作った現在値を最低8%ずつ
毎フレーム混ぜていた。各画素は16フレームに1回、自身の等倍レイで完全に置換される。それまでの15フレームへ
固定8%を適用すると、静止した正確な画素履歴の残存率は`0.92^15 = 0.286`となり、約71%が周囲の空間再構成へ
置き換わる。これは未採取画素の履歴を保つ設計と矛盾し、雲中の濃淡と雲底の房を低解像度の灰色へ拡散していた。

現在値へ寄せる割合は、現在と前フレームの対流位相差から求めた実変化量だけとした。位相差0では履歴を100%保ち、
差0.022では2.2%だけ追従する。カメラ移動はワールド位置の再投影、新規露出は履歴不採用、照明や天候の大きな変更は
CPU側の履歴無効化で別々に扱うため、固定下限で別レイを混ぜる必要はない。採取対象となった画素は従来どおり現在の
等倍値へ一度で置換する。

Debug単体試験`1526 / 1526`、Release単体試験`1522 / 1522`、Editor ABIと管理側Editorの両構成、通常C++の
Release検証実行に合格した。通常C++の雲中とEditorの地上表示では履歴由来の広いにじみが減ったが、縦長の煙状密度、
粒状の自己影、灰白色の平坦さは残る。時間再構成だけを合格とし、次は低周波形状の縦尺度と局所雲柱の連続性を

最小C++利用例は両構成でコンパイル・リンク・実行に合格した。ACS Frameworkの`f1ca498`も同じ配布物を明示して

## 低周波形状の上下連続性再監査

2026-08-27の再監査では、基本形状の`fullShapeColumnAt`が中央と水平方向4点だけを平均し、上下方向の
隣接形状を全く平滑化していなかった。雲の高さプロファイルとは別に、焼き込み済み3D形状の縦断面が急変するため、
同じ雲柱へ細い縦筋が残り、時間位相を動かしたときに柱状の陰影がちらつく余地があった。

現在は、中央1点、水平方向4点、上下方向2点の7点を`0.34 + 4*0.12 + 2*0.09 = 1.0`の重みで平均する。
これは焼き込み時だけの追加処理であり、通常の視線・光線の採取数、時間再構成の履歴、公開APIは変えない。
重み合計を単体試験で固定し、形状の平均密度を変えずに縦方向の高周波だけを落とす契約にした。

通常C++検証経路の地上視点では、修正前に見られた細い縦長の煙状部分が減り、隣接する雲塊が連続した大きな房として
見えることを確認した。上空視点は依然として長い視線区間による平坦な雲床が残るため、視覚品質は未合格とし、
次は上空からの雲頂受光と雲塊中心を確実に含む雲中検証を分けて監査する。なお、既存の雲中視点は層内高度だけを
保証し、天候場の雲塊中心までは保証していないため、その画面を「雲体内部」の合否証拠には使わない。

## 品質を保つ最適化規則

Ultra cloud optimization keeps the `0.25` trace scale, 384 view-sample ceiling,
8 light probes, sixteen-phase TSR, world-space density coordinates, and every
accepted probe position fixed. A candidate is retained only when the same
provenance-locked horizon/zenith/above harness shows a repeatable GPU improvement;
FXC instruction count is diagnostic evidence, not acceptance by itself.

視線レイは、包絡形状へ後段の高度、降水、作者密度、上層密度を全て掛けた完成密度上限が
`0.0015`以下の場合だけ空領域として飛ばす。形状だけの固定しきい値へ戻してはならない。
各追加形状領域の前に行う棄却は、未採取領域が形状を増やさないことを式で保証できる場合だけ使う。
新しい事前棄却は代数上の反例がないことに加え、同一の地上・天頂・上空入力でGPU時間を短縮し、
分岐発散によって採取削減を相殺しない場合だけ採用する。

最初の3個の光標本は採取間隔で侵食帯域を制限する。残り5個も位置、高さ分布、しきい値を変えず、影キャッシュが
利用できない場所では同じ式で正確に積分する。利用できる場所だけ、現在または直近3フレーム以内に
生成した遠距離の光学的深さへ置き換える。標本数、テクスチャ解像度、近距離の品質を減らす最適化ではない。

Curved-shell intersection also preserves the original factorized quadratic.
Camera position relative to the rebased tangent origin and the inner/outer
`c` terms depend only on camera, layer, and world origin, so the CPU writes
them once per frame. Each trace ray still solves the same two roots with the
same planet radius and chooses the same nearest continuous interval; only
duplicated per-pixel construction of those invariant terms is removed.

## Results and the 300 FPS target

`cloud-quality-summary.json` is the machine-readable result. The terminal table
reports, for each camera:

- observed Editor FPS average;
- FPS converted from the p95 observed frame interval;
- GPU throughput converted from average and p95 query milliseconds;
- cloud GPU average and peak milliseconds;
- input-priority retry, ready-after-retry, background fallback, and
  fairness-yield counts, plus the maximum backpressure epoch and peak presented
  burst.

The same summary also records the UTC capture time, OS and architecture, every
reported GPU adapter and driver version/date, and the canonical paths,
versions, sizes, timestamps, and SHA-256 hashes of `AcsEditor.exe`, its four
required runtime artifacts, and the `.acsproject`. All six inputs are hashed
immediately before and after each capture, then once more after all three captures.
Any checkpoint differing from the initial identity fails the affected scenario
and `ProvenanceGate`. The terminal provenance tables print the same artifact,
project, GPU, and driver identities, so a result cannot be compared without
seeing which renderer and machine produced it.

The 300 FPS target is informational by default. `TargetGate.Result` says
`MISS` when any view misses any of the four cadence/throughput checks, while
the script still succeeds if its quality and evidence gates pass. This keeps a
measured performance gap visible without mislabelling it as missing or corrupt
quality evidence.

For a release threshold, opt in explicitly:

```powershell
.\acs\scripts\profile_cloud_quality.ps1 `
  -EditorExe $editor -Project $project `
  -RequireTargetFps -TargetFps 300
```

With `-RequireTargetFps`, a target miss returns exit code 1. After PowerShell
parameter binding succeeds, input/path/setup errors return exit code 2.
Malformed parameter types and out-of-range values are rejected by PowerShell
before the harness can assign an exit code. The reported FPS is
render/presentation-call throughput; it is not a claim that the physical
monitor scanned out that many distinct images.

If an editor capture exceeds its soak plus startup-grace timeout, the harness
terminates the Windows process tree. A failed `taskkill` is checked by exit code
and falls back to terminating the root process instead of being treated as
successful cleanup. Editor launch uses `System.Diagnostics.Process.Start`
directly rather than `Start-Process -PassThru -Redirect*`, so Windows
PowerShell 5.1 reads the exit code from the same process object that performed
the launch. Standard output and error are copied concurrently to
create-new-only log files before waiting, preventing pipe deadlock and
preserving the no-overwrite guarantee.

## 積乱雲表面を消していた密度倍率の処理順

2026-08-26の密度再監査では、高さと降水による光学密度倍率を房変形・侵食より先に掛け、結果を0～1へ
収めていた。倍率は雲底かつ降水最大で`1.10 * 1.28 = 1.408`になる。たとえば縦分布と被覆を適用した
幾何密度`0.84`へ倍率`1.20`を先に掛けると`1.0`へ飽和し、強い侵食標本の下限`1.0 * 0.24 = 0.24`で再配置しても
密度は`1.0`のまま変化しない。積乱雲ほど表面の房と谷が消え、雲頂を滑らかな白い面へ戻す順序だった。

現在は、基本形状へ縦分布と被覆を一度だけ適用し、房変形と侵食を終えた幾何密度へ最後に光学密度倍率を
掛ける。同じ例では侵食後の幾何密度が約`0.789`、倍率適用後が約`0.947`となり、表面差を保つ。
詳細を無効にした場合は`clamp(density * scale, 0, 1)`が従来と同じなので、雲量と全体の光学厚を変更しない。
内側の包絡棄却も`envelopeDensity * densityScale`で判定し、倍率適用後に可視となる薄い縁を捨てない。

## 2D天候包絡と3D密度形状の高さずれ

2026-08-26の高さ再監査では、天候被覆を高度ごとにずらす旧処理と、それを全て削除した現在処理を
分けて評価した。天候被覆は局所雲底・雲頂を決める2D包絡なので、高度ごとに別の地点を採取すると
同じXZ柱の雲頂条件が標本自身の高度で変わる。旧処理の削除は正しい。一方、削除後は3D基本形状と
詳細形状にも風下方向の高さずれがなく、低周波被覆の輪郭が厚い層をほぼ真上へ押し出していた。

[Nubis 2017の密度モデル](https://advances.realtimerendering.com/s2017/Nubis%20-%20Authoring%20Realtime%20Volumetric%20Cloudscapes%20with%20the%20Decima%20Engine%20-%20Final%20.pdf)
は、天候被覆を動かさず、密度採取位置へ`height_fraction * wind_direction * 500 m`を加える。
現在はこの責務分離に合わせ、2D天候採取は高度非依存のまま維持し、基本形状と詳細形状のXZ座標だけを
下層上端で500 m、薄い上層上端で125 mずらす。方向`(0.9284767, 0.3713907)`は長さ1であり、
雲底ではずれ0、層内では高度に対して単調なので、形状を折り返さない。追加のテクスチャ採取はない。
これは縦に押し出された密度を傾ける修正であり、局所的な3D包絡を作者が配置できる状態ではない。

## 環境光の代替積分と層厚

2026-08-26の単位監査では、下層の環境光キャッシュと、キャッシュ外または上層で使う代替式を
独立に比較した。キャッシュは`密度 × 距離[m] × 0.00064[m^-1]`を積算した無次元の光学的厚さを
保持する。一方、旧代替式は`密度 × (0.35 + 0.65 × 高さ比)`だけであり、距離と基準消散係数を
欠いていた。このため900 mの薄層と9400 mの積乱雲層がほぼ同じ遮蔽になり、キャッシュ境界と
上層雲で照明の単位も一致していなかった。

現在の代替式は、局所雲柱の実厚を`層厚 × columnSpan`で復元し、局所高さから空・地面それぞれの
境界距離へ分けた後、`kVolumetricCloudReferenceExtinctionPerMeter`を掛ける。上下の光学的厚さの
和は常に局所雲柱の全厚と一致し、雲底では地面方向、雲頂では空方向が0になる。密度0.8、作者密度
2.1、層中央、局所幅1の例では、空方向の光学的厚さは900 mで約0.484、2500 mで約1.344、
9400 mで約5.053となる。キャッシュにも同じ均質密度を積算した場合は同じ値になるため、混合率を
変えても不連続を作らない。これは追加のテクスチャ採取を伴わない。

## 16位相の等倍標本を一度に置換していた周期ちらつきの再監査

2026-08-26の連続表示では、1/4寸法の時間方向超解像が各画素を16フレームに1回だけ採取し、
採取したフレームでは有効な履歴を現在の等倍標本へ100%置換していた。視線積分の開始位置を固定しても、
風移流と非剛体変形が進んだ16フレーム分の差は残る。その差を1画素ずつ直接表示するため、雲表面が
一瞬だけ粗くなって戻る周期変化として見えていた。以前の少数静止画で格子偏りが小さかったことは、
連続表示における時間方向の安定性を保証していなかった。

現在は、深度、空／雲の占有、不透明度が同じ雲体として受理された履歴を現在の3×3低解像度近傍へ
制限してから、現在標本を`w = saturate(0.28 + 2 d_e)`で反映する。`d_e`は既存の対流位相差である。
静止形状でも10回の採取後に残る旧値は`(1 - 0.28)^10 ≈ 3.74%`であり、旧20%案の約10.74%より短い。
対流差が大きい場合は重み1へ連続的に近づき、空と雲の入れ替わりは従来どおり履歴を棄却する。
履歴を使えない採取画素も、両側再構成へ100%切り替えず同じ重みで等倍標本を混ぜる。

同時に、4×4時間再構成でも等倍でもない任意の縮小倍率を、旧分岐が等倍追跡として扱っていた誤りを
修正した。この経路は全画素の現在再構成を毎フレーム持つため、近傍制限した履歴へ最低18%を反映する。
真の等倍追跡だけは、現在フレームの実レイをそのまま表示する。

`CloudRenderScale=1.0`、風速`1.0`の通常C++検証アプリを更新後のraw DX12実行物で起動し、地上視点を
24回連続採取した。隣接画像の平均明度差は約`0.43～0.52`階調、8階調を超えた画素率は最大約`0.033%`で、
画面全体が周期的に粗くなる変化は再現しなかった。一方、多数の縦柱と細かな雲塊は静止画にも明確に残る。
これは時間合成で隠す対象ではなく、全球の積乱雲指定を全被覆領域へ一様適用する空間形状の問題として
次の監査で分離する。raw DX12構成の単体試験はDebugで`1531 / 1531`、Releaseで`1527 / 1527`に合格した。
この修正を雲の完成とは扱わない。

## 積乱雲の局所成長と積雲上端プロファイルの再監査

2026-08-27の形状監査では、実装とテストで塔状成長の開始条件が異なっていた。シェーダーは雲種の
塔状成長を`0.84～0.99`で判定していたが、テスト側は`0.72～0.98`を使っていたため、テストが実際の
描画式を検証していなかった。テスト側の補助式をシェーダーへ揃え、雲種と降水量を混ぜた結果を同じ

また、天候の対流強度と雲内部の被覆強度を掛け合わせた局所発達値を、さらに同じ値で一度だけ絞った。
これにより、天候設定が広域で積乱雲を指定していても、成熟した雲中心以外は通常雲の高さへ戻る。
一方、通常の積雲は`0.62～0.94`から上端を減衰させ、中層の密度を高いまま縦に残さないようにした。
いずれも追加のテクスチャ採取や標本数増加はない。

この時点の画面確認では、通常C++実行の短時間連続表示で周期的な粗密変化は見られなかったが、

## 3D基本形状のタイル反復と高さ方向相関の再監査

2026-08-27の追加監査では、前回までの「縦柱」が時間再構成だけでなく、3D基本形状の空間周波数にも
残っていることを分離して確認した。診断時に天候被覆と高さプロファイルを固定し、形状テクスチャを直接
表示すると、水平断面は泡状のセルになる一方、高さ断面は高さ方向の進行距離が短く、同じ横位置の雲が
縦へ長くつながっていた。従来の倍率`layer.z * 0.0035`と下限`0.00012`では、検証アプリの設定
`0.035`が`0.0001225`となり、128セルのタイル周期は約`8.2 km`だった。

現在は物理層の寸法を変えず、基本形状の座標倍率を`layer.z * 0.0016`、範囲を`0.00004`～`0.00020`へ
見直した。同じ設定では`0.000056`、タイル周期は約`17.9 km`となり、同じ大形状が画面幅へ反復する回数を
減らす。下層の高さ方向変化率は`1.45`から`6.00`へ上げ、下層全体で水平断面と同程度の3D変化を確保する。
薄い上層は従来の`0.78`を保つため、上層を粒状にする変更ではない。

形状合成も、低周波Perlinの再マップを`0.46`～`0.62`から`0.40`～`0.72`へ広げ、4セルWorleyの房を
`0.35`～`0.75`で残すようにした。8・16セルの寄与は補助に留め、粒状の高周波で雲体を分断しない。
これは初回の128³焼き込み式だけを変更し、実行時の3Dテクスチャ採取回数、視線・光の採取数、GPU資源を
増やさない。CPUの座標倍率とテスト側の式も同じ値へ揃え、低倍率、異常値、単調なLOD境界を検査する。

固定天候の直接形状診断では、高さ断面の縦筋が泡状の塊へ分かれ、単一の横位置から長く垂れた柱は再現
しなかった。通常C++のDebug検証アプリでも地上視点の画面から規則的な縦柱は消えたが、雲層内では
まだ雲の密度が薄く、上空では雲頂の厚みと明暗が不足している。このため、今回の変更は3D基本形状の
タイル反復と高さ相関の修正として採用し、雲の完成や雲層内表示の合格とは扱わない。次は雲内の光学的な
包まれ感と、上空から見た雲頂の厚みを同じ形状場で監査する。

## 光源側光学的深さの密度単位をそろえた監査

2026-08-27の式監査では、光源側形状密度を積算した`lightDepth`と、設定された全体密度、
現在地点の局所密度を混同しやすい形で扱っていた。`lightDepth`はすでに形状密度と距離を積分した
無次元の値なので、局所密度をさらに掛けるのは二重計上になる。一方、設定された全体密度は光路全体へ
一度だけ必要であり、これまでの修正でそれまで外してしまうと、密度設定が太陽光の減衰へ反映されなくなる。
雲芯ほど光が過剰に遮られる問題と、設定密度を光路から失う問題を分離して修正した。

現在は、光源経路の終了判定と最終透過率を次のように揃える。

`tau_L = lightDepth * GlobalDensity * LightExtinction`

`lightDepth * GlobalDensity * terminationOcclusion > 18`

影キャッシュの平均深さと二つの光路の差も形状密度を積分した無次元量で保持しているため、キャッシュの
信頼度判定では現在地点の局所密度を再乗算しない。表示側と光源側の最終透過率には設定された全体密度を
一度だけ適用し、光路だけが別の雲濃度になる不整合を避ける。この修正は採取数や影キャッシュ解像度を
増やさず、雲の外へ密度を足さない。

修正後はDebug・Releaseの単体試験で旧式の再導入を検査し、通常C++検証アプリの地上・雲中・上空を
再撮影する。画面の雲中の房と上空の厚みが改善しても、それだけでUE級の完成品質や雲入りGIの完成とは
扱わない。

## 雲内部の低周波房の振幅を再監査

光学計算の式をそろえた後も、雲中の画面が広い灰色の面に見える問題が残った。詳細密度の最後にある
内部房の変調は、低周波の`detailFar`を使っていたが、係数が`0.90～1.10`、最大重みが`0.45`だった。
これは雲内部の密度差が最大でも約4.5%に収まり、光路積算と散乱でほぼ均される範囲だった。

現在は同じ低周波標本を`0.82～1.18`へ広げ、雲の中層から上部で最大重み`0.55`を掛ける。最大でも
密度の変調は約10%に留め、外形の包絡、雲底の凝結支持、侵食の下限は変更しない。高周波の`detailNear`
や新しいテクスチャ採取は追加せず、既存の連続した雲体の中へ大きな房と谷だけを戻すため、粒状の小塊や
柱状の新しい密度を外側へ発生させない。

この変更は、詳細密度の侵食後、光学密度の高さ・降水倍率を掛ける前に適用する順序を単体試験で固定する。
Debug単体試験と通常C++検証アプリの地上・雲中・上空を再確認し、房の視認性だけでなく、時間位相を動かした
ときの粗密反復が増えていないことも合格条件とする。雲の完成や積乱雲全体の形状完成とは扱わない。

## 上層雲の空側遮蔽を雲影キャッシュへ反映する監査

立体物用・環境光用の雲影キャッシュは、下層を32区間へ分けて空方向と地面方向の積算密度を保存している。
しかし上層雲が有効な場合も、列の位置を下層の雲底から雲頂へ固定していたため、下層の各点から空へ向かう
経路にある上層雲の遮蔽が`skyDepth`から抜けていた。光源側の直接影は別の雲層交差を使っていたため、
同じ雲でも直接光と環境光で上層の扱いが一致していなかった。

現在は上層が有効な列だけ、既存の32区間と同じ密度評価で上層全体の`upperColumnDepth`を一度積算し、
下層各点の空方向深さへ加える。下層と上層の間の晴天域は積算せず、下層の地面方向深さも変えないため、
空側だけへ存在する上層の遮蔽という幾何学的な関係を保つ。上層が無効な場合は追加ループを通らず、既存の
32区間コストと結果を維持する。

上層の密度、上層専用の1m当たり消散係数、曲面座標の再構成をソース文字列の順序検査で固定した。これは
TrueHDRIやGIを接続したときに、下層の雲底へ届く空からの放射輝度だけが過剰に明るくなる不整合を抑える
ための基礎修正であり、環境光そのものや外部HDRI素材の導入完了とは扱わない。

## 雲中の中層密度コントラスト監査

雲中視点を等倍と通常倍率の両方で確認した結果、時間差による粗密のちらつきは再現しなかったが、
中層の明暗が広い霧状へ均される課題が残った。外形密度を強くすると柱や粒が増えるため、外形の早期棄却や
雲縁のしきい値は変更せず、既に存在する密度だけを中層・天候中心で再マップする補正を追加した。

補正は`0`の空間へ密度を足さず、`1`の芯を超えない中心化変換である。表示密度だけに掛けると自己遮蔽が
別の形状になり、光の減衰と雲の見た目が不一致になるため、低詳細度の光学密度にも同じ関数を適用する。
採取数、詳細雑音の採取、時間位相、雲層の境界は変更しない。

通常倍率の雲中画面は変更前後で同一視点を比較し、1.2秒間の時間差で粗密が反復しないことを確認する。
等倍視点でも雲の局所的な明暗が同じ向きで出ることを条件とし、霧状の均一感が残る場合は、次の課題を
密度ではなく視線光学の減衰・局所視程として分離して監査する。今回の補正だけで雲中表現の完成とは扱わない。

## 雲中の大気区間を雲の積分と重複させない監査

雲中表示の合成経路を確認したところ、雲層内にカメラがあるかを判定する関数は存在していたが、合成段階では
使われていなかった。そのため雲の代表深度を、カメラから雲へ入る前の大気区間としてそのまま大気体積へ渡していた。
雲の視線散乱はカメラ位置から既に積分済みなので、同じ区間へ大気の前景散乱と透過を重ねると、雲中の明暗を
大気の灰色へ寄せる二重計上になる。

現在は大気対応の雲合成で、カメラが下層または上層の雲層内にある場合だけ前景大気距離を`0`へ固定し、雲層外では
従来どおり解決済み代表距離を使う。雲の不透明度、視線積分、採取数、時間履歴は変更しないため、雲そのものの光学と
背景大気の合成境界だけを分離している。大気体積が未接続の通常合成経路にはこの分岐を持ち込まない。

この変更は、雲中の灰色化を抑え、雲内部の局所照明を背景大気へ埋没させないための境界修正である。通常C++のDebug・
Release、Diligent構成の単体試験を通し、地上・雲中・上空で大気接続時の画面を再確認する。雲中の視程や積乱雲の
高さが完成したことを意味せず、画面で改善が弱い場合は、次に雲の代表深度ではなく前面到達距離を別途保持する設計を監査する。

## 雲形状の検証式を実装へ同期する監査

2026-08-27の再監査では、単体試験側の参照式が過去のシェーダー式を保持したままになっていた。対象は、低周波の高さ変化率、
局所的な積乱雲の発達、詳細房の最大変位、雲頂の局所変形、積乱雲の高さプロファイル、基本雑音の正規化である。これらが
古いままだと、実装を変更しても試験が通る一方で、実際の雲形状の正しさを保証できない。

検証側を製品シェーダーの式と同じ定数、順序、上下限へ揃えた。特に、密度のべき変換を正規化直後に一度だけ適用し、局所的な
積乱雲の発達を被覆の広域値と雲内部値の積から求め、雲頂の変位は雲種・降水・発達度の最大値から求める。積乱雲プロファイルの
胴体とかなとこ形状も、加算後の飽和処理と通常雲からの混合順を実装と一致させた。高さ変化率は層厚から求めた物理尺度と、
実装の最小・最大値による丸めを含めて検査する。

修正後はDiligent構成とraw DX12構成のDebug単体試験をそれぞれ実行し、両構成で1501件が合格した。これは検証式の取り違えを
除去したことを示すもので、雲の画面品質や積乱雲の完成を意味しない。次の形状改善では、この同期済みの参照式を基準に、地上・
雲中・上空の画面と数値の両方を比較する。

## 通常雲の雲頂支持を再監査

地上・上空の画面を確認すると、局所雲柱の上端まで高さを再配置している一方で、層積雲と積雲の高さプロファイルが0.90/0.94で
先に消えていた。既定の通常雲は層積雲寄りの天候値になるため、下層の雲頂0.88付近では密度がほとんど残らず、雲の実際の高さを
使っていても板状または粒の集合に見える状態だった。

局所雲柱の境界を越えて密度を足すのではなく、層積雲の減衰終端を0.98、積雲を0.995へ広げた。上端では従来どおり滑らかな三次補間
で0へ落とすため、雲柱の高さ、雲底、詳細房の振幅、採取数、時間位相は変更しない。通常雲の上部だけを先に失う不整合を解消し、上面の
厚みを読める範囲へ戻すための形状支持修正である。

参照式へ雲頂近傍と最上端の期待値を追加し、Diligentとraw DX12のDebug単体試験を通過させた。画面では地上・上空ともに雲の塊が
連続し、柱状の縦反復や時間経過による粗密の点滅が増えていないことを確認する。雲中の視程、積乱雲のかなとこ、TrueHDRI/GIとの
接続品質は別の受け入れ条件として扱う。

## 雲内部の環境光減衰を二重計上しない監査

雲内部の環境光は、空半球からの拡散輸送を近似する遮蔽係数と、視線・光源側の光路積算を別の役割として扱う必要がある。従来は
環境光へ使う遮蔽係数まで二乗していたため、空側の減衰を三次散乱相当の縮小率で再度掛け、雲底から中層へ届く明暗差を必要以上に
失っていた。結果として密度のある雲体が広い灰色面へ均され、形状を変えずに照明だけが平板化していた。

環境光の遮蔽は一段分の係数だけを使い、二乗は三次散乱の経路に限定した。表示側と光源側の積算密度、採取数、時間履歴、雲形状は
変更していないため、環境光の式だけを修正している。DebugのDiligent構成とraw DX12構成で、旧二乗式の再導入を検出する試験を含む
全単体試験に合格した。

画面確認では雲中・上空・地上の3視点を再撮影したが、内部の灰色化は軽減したものの、地上視点では雲塊が平たい楕円状に連なり、
上空視点では輪郭の連続性と上下の厚みがまだ不足していた。このため本修正は環境光の整合性を満たす小さな完了単位とし、雲形状の
完成や積乱雲の発達表現の完成とは扱わない。次の形状監査では、低周波の雲塊生成と高さ方向の連続性を分離して検証する。
