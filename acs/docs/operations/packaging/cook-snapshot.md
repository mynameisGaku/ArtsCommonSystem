# Cookスナップショットと公開境界

パッケージ作成は、長時間のCookとZIP生成の間に入力が変化しても、異なる世代のデータを1つの配布物へ混在させません。

## Cook入力の固定

正規シーンの`canonicalSceneAssetId`から必要アセットの閉包を構築し、順序を固定した依存関係グラフのハッシュを生成します。各必須アセットは、Asset DBが記録したサイズとSHA-256に一致する内容だけをCook入力として読み取ります。

正規シーンの解析、参照の書き換え、`main.acscene`の生成は、検証済みの同じシーン内容を使用します。処理途中で元のシーンを読み直して別世代の内容を混ぜることはありません。`Config`もファイルの相対パス、サイズ、SHA-256を持つスナップショットとして準備領域へ複製します。

## 依存関係の権威

Cook用のAsset DB更新は、アセット本体の内容を再計算し、`.acsmeta`を権威あるメタデータとして読み取ります。通常の参照走査対象では、ソースから発見した依存関係と`.acsmeta`の`dependencies`が一致しなければ`ASSET_METADATA_STALE`で停止します。

Blueprintの`.acsbp`だけは、ソースに記録された`PARENT`と`CMP`内のアセット参照を権威ある追加依存として閉包へ加えます。`.acsmeta`の依存関係も安全側の上位集合として保持するため、インポーターが記録した依存をソース走査だけで削りません。`PARENT`または`CMP`が不正、循環、欠落参照を含む場合は、部分的な閉包を公開せず失敗します。

`.acsdb/index.v1.json`は走査を速めるためのキャッシュです。壊れている、古いスキーマである、または安全に読めない場合は内容を破棄し、`ASSET_INDEX_CACHE_IGNORED`を警告として記録したうえで、アセット本体と`.acsmeta`から閉包を構築します。Cookの正否をこのキャッシュだけで決めることはありません。

依存走査とCook本体は、同じファイルから別々にバイト列を取得します。どちらもAsset DBスナップショットのサイズとSHA-256へ照合し、内容が異なれば停止します。Cook本体で取得した`verifiedSource`は、正規シーンの検査、参照の書き換え、Derived Data Cache入力、Cook出力に共用し、その途中で同じアセットを再取得しません。

## 公開直前の再検証

完成した一時ZIPを検証した後、ACSはアセット変更リースを即時取得し、公開が終わるまで保持します。その状態で次を再検証します。

- `.acsproject`の名前、スキーマ版、ACS版、`initialScene`、`canonicalSceneAssetId`
- `canonicalSceneAssetId`が示す正規シーンとCook済み正規シーンの一致
- 必要アセット閉包を再構築したグラフハッシュとCook時のグラフハッシュの一致
- `Config`スナップショットと現在の`Config`の一致
- 初期シーン移動記録が処理途中で追加されていないこと

すべて一致した場合だけ、一時ZIPを最終出力へ移動します。

## 変更を検出した場合

公開時に同一性を証明できない場合は、診断コード `PROJECT_CHANGED_DURING_PACKAGE` で公開を拒否します。対象には、プロジェクトマニフェスト、正規シーン、必要アセットの内容または依存メタデータ、`Config`の変更が含まれます。

必要アセット閉包へ到達しないアセットの内容変更はグラフハッシュを変えません。ただし、入力ツリー全体に対するパス、再解析ポイント、メタデータの安全性検査は引き続き適用します。

この変更リースはACSの処理同士を協調させる境界です。ファイルシステム全体を不可分に凍結する機能ではないため、各読み取りではサイズとSHA-256を検証し、公開直前にも再検証します。
