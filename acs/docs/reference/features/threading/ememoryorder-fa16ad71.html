EMemoryOrder

強いほど安全だが遅い。

列挙(enum)
対応するAPI: acs::EMemoryOrder

使う場面

ロックなしで安全に共有できる小さな値。 の各操作に渡す。 迷ったら既定の SeqCst でよい。 性能を詰める段階で緩める。

API項目

API項目 1

Relaxed
説明
順序保証なし。 値そのものは複数スレッドから同時に触っても途中状態が見えず、分割されずに完了する操作。 TAtomic が代表。だが、周りの読み書きの順序は守られない。 最速。
対応API
acs::EMemoryOrder::Relaxed 列挙値

API項目 2

Acquire
説明
このロード以降の読み書きが上に動かない。 Release された値を取り込む側。
対応API
acs::EMemoryOrder::Acquire 列挙値

API項目 3

Release
説明
このストア以前の読み書きが下に動かない。 書いた内容を他1 つのプログラム内で同時に進む実行の流れ。 複数あると処理を並列にできる。へ公開する側。
対応API
acs::EMemoryOrder::Release 列挙値

API項目 4

AcqRel
説明
読み書き両方を行う Read-Modify-Write。 読んで・変えて・書く、を一気にアトミックに行う操作(FetchAdd 等)。 操作向け(Acquire + Release)の意味AES-GCM が出力する 16 バイトの認証データ。 これが合わないとデータが改竄/破損とみなす。。 ただし ロックなしで安全に共有できる小さな値。 の Read-Modify-Write。 読んで・変えて・書く、を一気にアトミックに行う操作(FetchAdd 等)。(FetchAdd/Exchange/CompareExchange 等)は順序引数を取らない(x64 では常に完全GPU リソースの用途状態を切り替える同期。 ACS では普段は内部で自動管理される。)ため、この値を渡す先は Load/Store のみ。 Load は Relaxed 以外なら Acquire、Store は Relaxed 以外なら Release として扱われる(SeqCst も同じ扱いで、Load/Store に完全GPU リソースの用途状態を切り替える同期。 ACS では普段は内部で自動管理される。は入らない)。
対応API
acs::EMemoryOrder::AcqRel 列挙値

API項目 5

SeqCst
説明
全1 つのプログラム内で同時に進む実行の流れ。 複数あると処理を並列にできる。で唯一の順序が見える最強の保証。 既定値。
対応API
acs::EMemoryOrder::SeqCst 列挙値

使用例

a.Store(1, EMemoryOrder::Release);   // これ以前の書き込みを公開
u32 v = a.Load(EMemoryOrder::Acquire); // 公開された書き込みを取り込む
b.FetchAdd(1);                         // RMW(FetchAdd 等)は順序引数を取らない
