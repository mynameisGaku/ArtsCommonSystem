# FReplayDirector 永続化の安全契約

`FReplayDirector` はリプレイファイル、メタデータポインター、`FInputRecorder`、`FLockstep` を
信頼境界として扱う。保存と読み込みは例外に依存せず、上限検証、準備、原子的な反映の順で行う。

## 公開上限

| 対象 | 上限 |
|---|---:|
| リプレイ全体 | 256 MiB |
| 記録データとロックステップデータ | 各 128 MiB |
| 入力標本とロックステップフレーム | 各 1,000,000 件 |
| Tick 周波数 | 1〜1,000 Hz |
| リプレイパス | 1,023 UTF-16 コード単位 |
| ゲームバージョン | 64 バイト |
| レベル ID | 255 バイト |
| プレイヤー名 | 255 バイト |
| 検査値 | 空、または 16 桁の ASCII 16 進数 |

上限判定とサイズ計算は `u64` で行い、`u32` / `usize` へ縮約する前に検証する。
パスと C 文字列は公開上限までしか走査しない。

## リプレイのバイナリ形式

バージョン 1 のリプレイは次の完全一致形式である。全整数はリトルエンディアン。

```text
[magic "ACRP":4][version:4]
[seed:8][timestamp:8][duration_ticks:4]
[game_version_len:4][game_version]
[level_id_len:4][level_id]
[player_name_len:4][player_name]
[checksum_len:4][checksum]
[input_blob_size:4][input_blob]
[lockstep_blob_size:4][lockstep_blob]
[crc32:4]
```

CRC32 は末尾の検査値を除くリプレイ全体を対象とする。読み込み側は次の順で検証する。

1. ファイルサイズの正値、最小長、256 MiB 上限
2. マジック値とバージョン
3. 外側の CRC
4. 数値メタデータと各長さ付き文字列
5. 埋め込み NUL、フィールド別の長さ、検査値の正準形式
6. データ塊別の上限とリプレイ残量
7. 解析位置が CRC 直前と完全一致すること
8. 内側データのマジック値、バージョン、Tick 周波数、件数、完全サイズ、内側の CRC
9. 全準備領域の確保

途中まで正しい接頭部の後ろにバイト列を追加し CRC を再計算したファイルも、解析位置の完全一致で拒否する。
最初の全バイト読み取り後にファイルサイズを再取得し、現在位置から 1 バイトの EOF 試し読みも行うため、
読み込み中の伸長または短縮を成功したスナップショットとして反映しない。

## トランザクション読み込み

`TryLoadReplay` はファイルスナップショットをプロセスヒープへ読み、`FReplayDirector` が所有する文字列を一時
`FString` へ構築する。既存の所有文字列、メタデータ、モード、Tick はここでは変更しない。

`FInputRecorder::TryLoadFromBuffer` と `FLockstep::TryLoadFromBuffer` は、
全バイナリ形式の検証後に同じアロケーターを使う一時 `TArray` へ全レコードを復元する。
`TryReserve` / `TryPushBack` のどちらかが失敗した場合、対象データ元の既存状態は不変である。

リプレイ読み込みでは、注入された 2 つのデータ元をそれぞれ一時インスタンスへ読み込む。
各一時インスタンスは置換先と同じアロケーターを使うため、反映後に短寿命アロケーターへの参照を残さない。
両方が成功した後だけ、非公開で失敗しない `SwapLoadedState` により既存のデータ元へ一括反映する。
これにより「記録データ成功後にロックステップ側がメモリ不足」という順序でも、両データ元と `FReplayDirector` の状態は変化しない。
交換対象は永続化状態だけで、各データ元の実行モードは維持する。

最後に所有メタデータをムーブし、ポインターを新しい所有バッファーへ張り直して
`Idle / current_tick=0` を反映する。

既存の `LoadReplay` は互換ラッパーとして `TryLoadReplay` へ委譲する。

## 検証付き記録メタデータ

`TryStartRecording` はメタデータポインターを上限付きで走査し、4 文字列を一時領域へ複製してから
`Recording` へ遷移する。呼び出し側の元バッファーを後で変更しても `FReplayDirector` のメタデータには影響しない。
不正な検査値、上限超過、メモリ不足、誤ったモードでは既存セッションを変更しない。

既存の `StartRecording` は互換ラッパーとして検査付き API へ委譲する。

## 原子的な保存

`TrySaveReplay` はデータ元の件数から内側データの正確な必要長を計算し、次を確認する。

- データ元の `SaveToBuffer` が申告長を完全に書いたこと
- 生成された内側データ自身のマジック値、バージョン、サイズ、CRC
- メタデータとリプレイ全体の上限
- リプレイ用バッファーを一度だけ確保し、位置が計算済み総長と一致すること

ディスクへの反映手順は次のとおり。

1. 保存先と同じディレクトリに `<path>.tmp.<pid>.<tid>.<nonce>` を組み立てる
2. `CREATE_NEW` で一時ファイルを作り、既存ファイルまたは再解析ポイントを上書きしない
3. 全バイトを書き、部分的な書き込みを拒否する
4. `FlushFileBuffers` の成功を確認する
5. `CloseHandle` の成功を確認する
6. `MoveFileExW(MOVEFILE_REPLACE_EXISTING | MOVEFILE_WRITE_THROUGH)` で原子的に置換する
7. 開いている旧スナップショットがある場合は、`FileRenameInfoEx` に実装内の
   `kReplaceIfExists | kPosixSemantics` を指定する方式へ切り替える

書き込み、永続化、終了、置換のどこで失敗しても一時ファイルを削除し、既存保存先を変更しない。
`FInputRecorder` / `FLockstep` の `SaveToBuffer` も容量、全上限、保存対象の浮動小数点数が有限値で
あることを検証してから書き始める。読み込みも NaN と正負の無限大を拒否する。
失敗時は `out_written=0` かつ出力バッファー不変である。

既存の `SaveReplay` は互換ラッパーとして `TrySaveReplay` へ委譲する。

## Tick の数値安全性

`Tick` は非正値、NaN、60 秒を超える異常な時間差を無視する。
Tick 加算はオーバーフロー前に飽和または継続時間へ範囲制限し、巨大な時間差からの浮動小数点数から整数への変換や
`u32` の周回を発生させない。

## 回帰テスト

`tests/replay_director_safety_tests.cpp` は以下を検証する。

- メタデータの所有コピー、上限、検査値、失敗時の状態不変
- 保存と読み込みの往復
- CRC 改変、切り詰め、CRC 再計算済みの末尾バイト、過大なメタデータ長
- 256 MiB 超の疎ファイルを確保前に拒否
- 下位データ元の読み込み中に起きるメモリ不足のトランザクションと保存出力不変
- 記録データの準備成功後にロックステップ側がメモリ不足でも、2 つのデータ元と `FReplayDirector` がすべて不変
- 読み取り側が原子的な置換を拒む状況で既存リプレイが保持されること
- 削除共有付きの読み取り側が旧スナップショットを保持し、パスからは新リプレイを読めること
