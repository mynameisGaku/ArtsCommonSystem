# アセットインポートの永続化契約

ACS Editor のアセットインポートは、設定プロファイル、変換レシピ、Derived Data Cache、
アセット本体と `.acsmeta` の公開を別の境界として検証します。操作方法は
[アセットのインポート設定](../../guides/assets/import-settings.md)を参照してください。

## 設定プロファイル

最後に確定した設定は次のプロジェクト内パスへ保存します。

```text
Saved/Editor/AssetImporterSettings.v1.json
```

プロファイルはスキーマバージョン 1、UTF-8 BOM なし、最大 64 KiB です。固定されたプロパティだけを
受理し、未知または重複したプロパティ、必須値の欠落、不正な型、非有限の倍率、未対応の列挙値と
サンプルレートを拒否します。読み込みに失敗した場合は安全な既定値を使い、部分的な設定を採用しません。

保存時は設定を正規化してから、同じディレクトリに一意な一時ファイルを `CreateNew` で作成します。
`WriteThrough` とディスクへのフラッシュが完了した後にだけ、確定済みプロファイルを置換します。
途中で失敗しても既存プロファイルは保持され、一時ファイルだけが削除対象になります。

プロジェクトルート、`Saved`、`Editor`、既存プロファイルは通常のディレクトリまたはファイルでなければ
なりません。再解析ポイントを経由するパスは読み込みにも保存にも使いません。

## プロジェクト境界と設定スナップショット

Asset Viewが別のプロジェクトへ切り替わると、プロジェクト世代を進め、以前の読み込みとアセット操作を取り消し、メモリ上の設定を`AssetImporterSettings.Default`へ戻します。保存済みプロファイルはワーカースレッドで読み込み、開始時と同じプロジェクト世代であり、取消されていない場合だけメモリへ反映します。以前のプロジェクトから遅れて完了した読み込み結果は採用しません。

`Import`開始時には、`Project`、Asset Database、`AssetImporterSettings`、入力パス、プロジェクト世代、取消トークンを固定します。`AssetImporterSettings`は不変な値として処理手順へ渡されるため、処理中のUI変更や後続のプロジェクト切替を参照しません。フォルダーを再帰的に取り込む場合も、すべての入力へ同じ設定スナップショットを使います。

インポート処理用のワーカースレッドは、設定プロファイルの原子的な保存を完了してから`AssetImportWorkflow`を開始します。プロファイルを保存できない場合はアセット本体、`.acsmeta`、Asset Databaseを変更せずに`Import`を中止します。`Import`完了後の一覧更新も、開始時と同じプロジェクト世代かつ同じAsset Databaseである場合だけ行います。

## レシピの識別子

`AssetImporterRecipeContract` はインポーター名を `Trim()` 後に小文字化し、インポーターバージョンと
正規化済み設定を名前の序数順に並べます。正準文字列では各名前と値の前に .NET の
`string.Length`、つまり UTF-16 コード単位数を付けます。その文字列全体を UTF-8 へ変換してから
SHA-256 へ入力します。出力先パスは入力しないため、同じソース内容と設定を持つアセットは移動や
名前変更の前後で同じレシピになります。

処理済みアーティファクトへ渡す設定は、次の順で検証します。

1. 動的設定を含む入力全体を数え、128 件を超えた時点で拒否する
2. 名前と値へ `Trim()` を適用し、名前は最大 256、値は最大 4,096 UTF-16 コード単位に制限する
3. `Trim()` 後の名前と値を UTF-8 へ変換したバイト数を動的設定も含めて合計し、192 KiB を超えた時点で拒否する
4. `sourceContentHash`、`sourceLastWriteUtcTicks`、`sourceSizeBytes`、`processed*` を大文字小文字を区別せず動的設定として除外する
5. 残った設定の重複名を拒否する
6. レシピ識別子の計算時に `recipeHash` を除外し、名前は最大 64、値は最大 1,024 UTF-16 コード単位に制限する

宣言済みの `recipeHash` は正しい SHA-256 形式で、同じ正規化済み設定から計算した値と一致する場合だけ
受理します。動的メタデータはレシピ識別子へ混ぜず、検証後の値で置き換えます。

## Derived Data Cache のエンベロープ

処理済みアーティファクトは次のプロジェクト内パスへ格納します。

```text
Temp/DerivedDataCache/AssetImports/v1/<先頭2文字>/<key>.acsimpddc
```

`key` は処理契約、アセット種別、ソース拡張子、インポーター名とバージョン、検証済みレシピの
SHA-256、ソースの SHA-256 とバイト数から決まります。ソースパスと出力先パスは含みません。

エンベロープは次の順序です。整数はリトルエンディアンです。

| フィールド | サイズ | 検証 |
| --- | ---: | --- |
| マジック値 | 8 バイト | `ACSIDD1\n` と完全一致 |
| スキーマ | 4 バイト | `1` と完全一致 |
| キー | 32 バイト | ファイル名の `key` と完全一致 |
| データ本体の SHA-256 | 32 バイト | 読み取ったデータ本体から再計算 |
| データ本体長 | 4 バイト | 0 以上 256 KiB 以下 |
| データ本体 | 可変 | 申告長とファイル末尾が完全一致 |

不正な既存エントリはキャッシュヒットとして扱わず、正規形から再構築します。書き込みは
同じディレクトリの一意な一時ファイルへ行い、`WriteThrough` とフラッシュ後に置換します。
同じキーを並行生成した場合は、先に公開された内容が要求された正規形と完全一致するときだけ受理します。

## パスとファイル実体の検証

キャッシュの各ディレクトリはプロジェクトルート内に閉じ、経路上の全区間で再解析ポイントを拒否します。
ステージ済みソース、キャッシュエントリ、一時ファイルも通常ファイルでなければなりません。
さらに、ファイルを開いた後にハンドルから実体の属性と最終パスを取得し、検査したパスと同じ実体を
開いたことを確認します。検査とオープンの間に別の実体へ差し替えられた場合は処理を中止します。

## 段階的な公開とロールバック

`AssetImportWorkflow` は一つの入力を次の順で公開します。

1. ソースを非公開のステージング領域へコピーし、長さと SHA-256 を確定する
2. ステージ済みソースを再検証し、処理済みアーティファクトを構築または再利用する
3. レシピと処理済みアーティファクト情報を含む `.acsmeta` を準備する
4. 公開先、長さ、SHA-256、現在段階を持つジャーナルを永続化する
5. アセット本体を公開し、長さと SHA-256 を再検証してジャーナルを進める
6. `.acsmeta` を公開し、SHA-256 を再検証してジャーナルを進める
7. Asset Database の索引を一括更新する
8. 完了したステージング領域を削除する

キャンセル、メタデータ公開失敗、索引更新失敗では、この処理で公開した項目を逆順に戻します。
ロールバックはジャーナルの長さと SHA-256 に一致するファイルだけを削除します。公開後に内容が変わった
ファイルや判断できない状態は削除せず、ジャーナルを残して通常のインポートを停止します。
再開時の整合処理は、一致する本体とメタデータを完成させるか、未公開の準備だけを破棄します。
