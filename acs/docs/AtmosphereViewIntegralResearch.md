## 分離する入力と出力

太陽方向と視線方向をともに鉛直上向きとし、地表反射、多重散乱、太陽円盤を含めない単散乱を調べる。
CPUは公開`CAtmosphere::EvaluateSkyRadiance`、GPUは現製品の`EvaluatePhysicalSky`を呼ぶ。
高度、太陽入射量、評価点数を入力とし、線形RGBの放射輝度を出力とする。ゲームやEditorの状態には依存させない。

距離は本書ではkmへ統一する。CPU公開高度はmなので1000倍して渡し、GPUにはkmを渡す。
地表半径は6360km、大気上端高度Hは100km。係数の単位はkmの逆数である。
入射量Sは現製品の平行な太陽光を表す係数であり、太陽円盤の単位立体角当たりの輝度とは区別する。
APIの「ピーク輝度」というコメントは式と不整合だったため、放射照度へ訂正した。太陽円盤側の量との実装上の統一は別途必要である。

## 解析解

視点高度をh0、散乱点高度をhとする。同じ鉛直光路なので、乗法性により

```text
T(h0,h) T(h,H) = T(h0,H)
```

となり、散乱位置から独立になる。レイリー／ミー密度の積分量をCR／CM、オゾンをCOとすると、

```text
Cj = Hj exp(-h0/Hj) [-expm1(-(H-h0)/Hj)]
CRのHj = 8km、CMのHj = 1.2km
T = exp[-(βR CR + βMext CM + βO CO)]
L = S T [βR PR(1) CR + βMscat PM(1) CM]
```

オゾン密度は高度10／25／40kmで0／1／0の三角形。COはh0より上の残り面積を直接求める。
PR(1)=3/(8π)。ACSのミー位相はg=0.8のHenyey–GreensteinなのでPM(1)=(1+g)/(4π(1−g)²)。
βMext=0.0044、βMscat=0.003996を混同せず、散乱を消散へもう一度加算しない。
入射光子は−太陽方向、出射光子は−視線方向へ進むため、今回の散乱角の余弦は+1である。

S=(1,1,1)の独立した倍精度計算例：

## 先行試験の契約

高度0／1.2／8／10／25／40／80／90／99.9375／100kmと、色別の入射量を使う。
高度100kmでは厳密0、それより下では有限かつ正値を要求する。
初期の相対誤差目標は0.1%。絶対誤差だけで高高度の微小な光を0へ潰す実装を通さない。
GPUの現16点、CPUの標準32点を基準とし、単なる点数増加を修正としない。
CPUの0点指定から1点への互換動作、入射量への線形性、太陽積分の評価点数依存も分離して検査する。

既存の50区間試験は視線の中点近似を固定した消散係数の回帰試験であり、連続積分の精度保証ではない。
視線アルゴリズムを変えると期待値の前提も変わるため、その試験を無説明に削除・許容差拡大せず、
新しい解析解の試験へ係数検査の責務を引き継ぐ必要がある。

別の処理順の不具合として、CPUは太陽遮蔽時のcontinueで視線側の消散更新も飛ばしている。
太陽が届かない場所も奥の散乱光を減衰させるため、散乱源が0であることと媒質が存在しないことは区別する必要がある。
例えば正規化した太陽方向のyが−0.05なら、鉛直上向き光路は地表から約7.965kmまで地球の影になる。
この問題は鉛直上向きの太陽だけでは検出できず、影のある入力の独立積分を別のRedとして用意する。
鉛直光路で高さ0kmと6kmの二視点を選ぶと、その間は全て地球の影なので、L(0)=T(0,6)×L(6)が成り立つ。
T(0,6)は指数密度とオゾンの解析積分で独立に求められる。太陽側の数値積分を正解として複製する必要はない。
旧法の対照には地表側1000区間／6km側940区間を使い、共通の100m幅にして明るい部分の標本位置をそろえる案がある。
これは影区間の消散を切り出す試験であり、製品の点数増加による解決案ではない。実際の交点と標本の一致は別途確認する。

また、区間内の太陽透過率を中点に固定して視線透過だけ解析積分しても、積全体の厳密積分にはならない。
同方向・一定媒質の局所例でも、真の値への倍率はsinh(Δτ/2)/(Δτ/2)>1となる。
密度に沿う求積ではR/Mそれぞれの重みと、同じ標本位置のTview×Tsunを評価し、重みを距離順の区間幅へ読み替えない。

## 一次資料と適用範囲

[Brunetonの著者実装](https://ebruneton.github.io/precomputed_atmospheric_scattering/atmosphere/functions.glsl.html)の
透過率と単散乱の節を読み、太陽から散乱点、散乱点から視点の二つの透過率を掛ける順序を照合した。
そこで使われる50区間の台形則は、ACSの16点で十分という証明ではない。また著者実装のミー位相は
Cornette–Shanks型で、ACSのHenyey–Greenstein型とは異なる。位相の値をそのまま参照へコピーしない。

[PBRT第4版の透過率](https://pbr-book.org/4ed/Volume_Scattering/Transmittance)も光路分割の乗法性を説明する。
閲覧時の数式表示に欠落があるため、本文で確認できる性質と上記の独立導出を区別する。
同ページの光学的厚さ推定を指数化する際の偏りの向きには、凸性から得る不等式と食い違って見える記述がある。
この段落は根拠として採用しない。資料名や掲載だけで全主張を正しいと扱わない。

鉛直の解析解だけでは斜め・地平線・地中の打切り・太陽遮蔽境界の精度は保証できない。
次の実装では密度に沿う求積と透過率の積を検討するが、まず現製品のRedを保存してから変更する。
地上／上空／雲内の画像、連続フレーム、実解像度の性能、配布物・外部Frameworkは別の受入条件である。

最低高度hmin、そこから最接近点までの距離p、半径r=R+hmin、密度高さaに対して、

```text
w = 1-exp(-Δh/a)
u = sqrt(p²+2ra w)-p
Δh = -a log1p(-w)
s = sqrt(p²+Δh(2r+Δh))-p
ρ(h) ds = exp(-hmin/a) [(p+u)(1+Δh/r)/(p+s)] du
```

を使う。平方根同士の差は二乗差による式へ直し、小さい密度変化はexpm1／対応する級数で保持する。

## 影の区間分割と次の反例

視線O+tVと平行な太陽方向Sについて、影円柱は次式の内部になる。

```text
A = |V×S|²
B = (O×S)·(V×S)
C = |O×S|²-R²|S|²
A t²+2B t+C < 0 かつ (O+tV)·S < 0
```

根は相殺の少ないqの式で求め、地表または大気上端までの有限視線へ切る。
影がない場合にもclamp(-B/A,0,L)を幅0の分割点として残し、接触時に一つの求積から二つへ急に切り替えない。
GPUは地表直上の視点O=(0,R+h,0)に限定し、判別式の大きい半径二乗の減算を高度hの式へ展開して補償演算する。
この根の精度を、有限地表判定で保証した厳密な整数符号と同一視しない。
影の手前・奥へ各帯の点数を固定して配るため、影が視線途中にあると積分点数と負荷は増える。

`shadow-clip-debug.log`／`shadow-clip-release.log`は13成功・0失敗。

高度40kmの青の透過関係も相対約5.4e-6まで改善した。地上／雲内の画像上のちらつき全般の解決ではない。
この時点のSky.cppは`9E8D74FC30D43FA2EDB31203A9A1F5F658760F2FB587296EC5B545D52B2DB692`、
Atmosphere.cppは`5D9C95D299BC3822F0BEA4BC2D5E084B98819E33C65F69914CF8E47C4D01ECC7`。

続いて視線と太陽を同方向に保ち、(高度km,天頂余弦)=(0,0)/(0,.05)/(0,.2)/(20,-.05)/(80,-.14)を追加した。

## 非鉛直の精度に向けた次の検討

共有の密度列積分にも誤差がある。地上水平の8点評価は分子282.937594km／微粒子109.537665kmで、
独立積分282.838135km／109.498922kmより大きい。光学的厚さを指数化するため、密度列の相対誤差をそのまま光の誤差上界にできない。

[Yue 2024の本文](https://acp.copernicus.org/articles/24/5093/2024/)を再確認した。
球面密度を半径変化の積分へ移す考え方は参考になるが、式10で近似が入り、評価範囲での最大0.5%は今回の放射輝度0.1%を保証しない。
近似式を厳密な正解や万能の置換として採用しない。
[mpmathの公式解説](https://mpmath.org/doc/current/calculus/integration.html)も、途中の不連続と端点で急変する関数を区別して扱い、分割や誤差推定だけでは正しさを保証しない例を示している。

次は、密度座標の高高度端に残る対数由来の急変をu=U v(2-v)で緩める変換と、
粗い視線標本が密度の総量を変えないようにする0次の積分条件を検討する。
許容誤差を広げたり、太陽色や散乱係数を調整して反例を消す方針は取らない。

## 端点・密度総量・影判定の追加修正

密度列を二次の座標変換で評価し、上端の補余量を次式から直接求めた。

```text
u = U v(2-v)
1-w = exp(-Δh/H) + U(1-v)²(U+u+2p)/(2rH)
```

丸め済みのwを1から引かない。小さいw側には既存のlog1p相当を使う。
また視線の積分は、密度列Cと密度重みwによる `C Σ(w Tview Tsun)/Σw` とした。
分母には極小の基底密度を含めず、影の標本が0となっても分母から媒質を除かない。
これは密度総量を保存するが、変化する透過率を正確に積分できることの証明ではない。

二次変換だけではCPU1点の鉛直解析形との接続が崩れた。
`vertical-join-red-debug.log`は14成功・1失敗で、水平成分1e-5を加えただけでも新しい段差が出た。
Jの既知一次成分 `1+u/r` を解析積分し、残差だけを求積する方式へ直した。
これによりsun_steps=1／3／9の末尾1点でも、鉛直への接続を保つ。

影の判別式を作る外積にも先行丸めがあった。独立監査の二つの入力を実GPUで再現した。
`shadow-cross-red-debug.log`では、約357mある影が幅0となり、影なしの別入力には約394mの幅が生じた。
外積の積・差から上下位を保持してから判別式を評価する修正後、`endpoint-cross-debug.log`で両反例が通った。
密度総量保存後の`moment-debug.log`は14成功・0失敗で、非鉛直5条件も成功した。

ただし、幅0の分割点を単に頂点へ置く方法は、視線と太陽が平行になると別の不連続を生んだ。
`parallel-join-red-debug.log`で、影のない反平行近傍の緑・青が最大約0.196%跳ぶことを実GPUで確認した。
影なしの全分岐で、有限区間内の最接近位置c0と円柱・昼側平面からの隔たりを使う分割規則へ統一した。

```text
c0 = clamp(-B/A, 0, L)
F0 = C                       （c0=0）
F0 = -Δ/A                    （0<c0<L）
G = max(F0,0) + max(P(c0),0)²
f = clamp(c0 + sqrt(G/A), 0, L)
```

c0=L、またはG>=A(L-c0)²なら、大きい除算をする前にf=Lとする。A=0の影なしもf=L。
通常の影発生時にはG→0となって接触位置へつながり、A→0・C≠0の影なしでは区間端へつながる。
`shadow-gap-debug.log`は15成功・0失敗。反平行近傍の最大相対差は約9e-7まで減った。
一方、A=0=Cへ高度も同時に近づける前方の退化入力はこの連続性の確認範囲外である。
物理的には連続な前方光路も含まれるため、全てを「点太陽の物理的な影の不連続」で説明しない。

## 連続性試験では見えなかった絶対値の誤差

大きい項を先に扱うFastTwoSumの分岐版は、単独加算v9では10組とも合格したが、
組合せた影v6/v10では判別式が正しい約0.031939711ではなく0.131502494となる。
三項演算への置換だけを製品へ採用せず、組合せた計算でも丸めの回収を保証できる方式を調べる。
条件式で項を選ぶv5はFXCの不正な命令修飾エラーでコンパイル不能だった。いずれも一時実験だけで、製品の加算式は未変更。

証拠の注意: `shadow-ieee-v4-release.log`は検査口のビルド失敗後に旧実行物が動いた無効な実験であり、上記の`-valid-`版だけを使う。
その旧実行で`shadow-rhi-v3`三ファイルも上書きされたため、現在の三ファイルをv3の途中値根拠にはしない。
元の`shadow-primitives-v3.hlsl`と`shadow-primitives-v3-release.log`は保持されている。v1/v2/v7/v8/v9/v10は別名の証拠として保持する。

### DXIL経路との比較（製品採用ではなく検査口の実験）

同じ2件をDebugライブラリーへ結び直した`sum-and-shadow-red-debug.log`は2成功・0失敗。
Releaseの不合格をDebugの成功で覆わない。既存のGPU選好を外す実験でも同じRTX 4070 SUPERが選ばれたため、別GPUの確認にはなっていない。

SDK同梱DXCで元のHLSLをSM6.0、O3、Gesでコンパイルし、既存`IRhiShader`を実装した一時アダプターから同じRHIへ渡した。
`sum-dxc-v11-release.log`と`shadow-dxc-v11-release.log`はそれぞれ1成功・0失敗。
式・係数・許容誤差を変更せず、影の判別式は0.0319397114217へ戻った。
FXC/DXBC経路とDXC/DXIL経路の差は確認できるが、どの内部変換に欠陥があるかは断定しない。

一時入口`sky-dxc-suite.cpp`では製品の18テストをそのまま登録した。
計算シェーダーの作成をDXIL読み込みへ、公開描画の初期化だけを`CSky::InitWithCompiledShaders`へ差し替え、
定数設定・命令提出・透過計算・公開描画・読戻し・期待値は製品の実装を使用する。
最初の`dxc-suite-v12-extraction.log`はHLSL保存用の9成功・9失敗であり、描画の成功記録ではない。
10入口を別途DXCで作成した後の`dxc-suite-v12-release.log`は**18成功・0失敗**。
有限光路、薄明の絶対値、曲がった視線、実GPUの共有媒質、2×2画素の公開描画13条件を含む。
これは既存RHIと公開描画器へ接続する実験であり、製品のDXCロード・配布・Editor起動や実画面の性能を検証したものではない。

同じ候補`physical-sky-priority.hlsl`のPSMainをDXCで一回測定すると1.127秒、108268バイトだった。
v12で現在のHLSLを使ったPSMainも約1.14秒、視線積分の検査入口は約1.66秒。
数百秒の作成費用を解消する有力な経路だが、全画面でのGPU描画費用とは別に扱う。
v12のPSMainソースSHA-256は`6D53430CE7367341DD67A6B04DCAEB6114D71C75A1294293C8647523DF811EC8`、
出力DXILは`54CF1D5F975DAE86431AD490FD0AF94BA1720021E19EF317C3379C12E0E28BBF`。
CPU側は検査口を結び付けた時点のReleaseライブラリーであり、並列担当による後続の区間選択修正はこの18成功に含めない。

依存監査では、既存`FShaderDesc.target`で明示SM6を選択すれば公開fieldを増やさず構成できる一方、採用前に次が必要と分かった。

- RawDX12用のDXC/DXILの版固定・ライセンス・安全なロード場所・配置済み製品での検証。
- Feature Level 12_0だけでなくShader Model照会、事前コンパイル経由を含むPSO作成時の失敗伝搬。
- DXC欠落・非対応環境で、誤判定する既存経路へ黙って戻らない契約。
- `desc.target`を無視して5.1へ固定するDiligent経路の整合と、Vulkanを含む個別検証。
- 通常C++、Editor ABI、非同期コンパイル中の終了、配布ZIPでのDLL収録の検証。

以上は未完了。SDKに存在するDLLで検査が通ったことを、そのまま再配布可能性や製品対応の証明にはしない。

### 未達の色への区間配分（CPU/GPUの限定修正）

CPUの選択処理を`AtmosphereAdaptiveIntegrationInternal.h`へ切り出し、製品が呼ぶ関数へ先行試験を追加した。
区間の状態は従来の呼出し内配列が所有し、公開構造体やsubsystem、STL、friendは追加しない。
別担当の`Temp/cpu-adaptive-selector-20260912/red-debug.log`は6件中4件が不合格で、
指定反例で区間0を選び、残り43分割がRへ偏ることを再現した。
許容内の色を優先度計算から除いた後の`green-debug.log`と`green-release.log`は、ともに6成功・0失敗。
反例の模擬求積ではR分割0、G分割21、42区間でG誤差9.875e-5へ到達する。
色の入替、相対順位、許容境界、区間数0、上限、零値、同率、分割不能も含む。模擬求積は実際の散乱積分の精度証明ではない。

GPUでは一つの候補の優先度だけを`PhysicalAdaptiveErrorPriority`へ切り出した。
配列を別のHLSL関数へ渡して複製させず、区間の配列所有と走査は元の求積関数に残す。
旧式で実行した`adaptive-priority-red-release.log`は5比較が不合格。
未達のRGBだけを比較する変更後、`adaptive-priority-green-release.log`は4条件を含む1件が合格した。
求積本体の値・誤差・許容値・上限64は変えていない。

独立監査は、マスクが一時的な候補優先度だけへ作用し、保存した全RGB誤差を消さないことを確認した。
CPU/GPUとも分割後に全区間を再集計するため、許容内だった色が再び未達になれば選択へ戻る。
分割不能な区間も値と誤差の総和には残り、上限へ達した最後の子も評価してから終了する。
前提は非負有限の総量・誤差・許容値、現在の区間と一致する集計値、正しい配列長、内部または始点へ正規化された分割位置である。
CPUは最終RGBだけを返すため、残留誤差・終了理由を外部から観測できないという既存の診断上の制約は残る。

Releaseの大気テストを再ビルドし、CPU側にもこの変更を取り込んだ。
既存RHIへDXILを渡す検査口での`dxc-suite-v13-release.log`は19成功・0失敗。
v13は11入口を現在のソースから再生成し、v12の出力を流用していない。
通常のFXC経路の加算残差問題や製品DXC対応の未完了は、依然として別の受入阻害要因である。
